\section{Motivation}\label{sec:intro-motivation}

Engineering systems often describe one product with several models. Examples are
the CAD geometry, a simulation mesh and a written specification. These models
overlap, because the same fact about the product appears in more than one of
them. Consistency Preservation Rules (CPRs) keep the models in agreement. They
take an update made in one model and propagate it to every model that shares the
changed resource.

When many updates run at the same time, there are two ways to apply a change.
The first way is consistent but slow. The change is accepted only after every
affected model is ready to apply it. The more models a change reaches, the
longer this takes, so performance drops sharply as the number of models
grows~\cite{zacouris2026mxs}. The second way is fast. The change is accepted
immediately, and the work of propagating it is moved to the background. This
background work is called \emph{reconciliation}. Until it is done, the other
models that share the resource still show the old state. They see the change
only after some delay.

In transactional systems these two ways are known as ACID and BASE.
Chapter~\ref{chapter:preliminaries} introduces both in detail. This thesis
combines them in one system. The goal is to find a point between the two that is
faster than the consistent way alone, while the delay in the other models stays
within a limit that the system administrator accepts.

\section{Formal problem statement}\label{sec:intro-problem}\label{sec:intro-formal}

The delay of the background updates may leave some resources out of date. This thesis
measures this inconsistency as the share of resources that are out of date. We
call this share the \emph{dirty fraction} $d$
(Section~\ref{sec:prelim-inconsistency}). Let $c$ be the \emph{critical dirty
  threshold}, which means highest dirty fraction
that the system administrator accepts. The task is to build a mechanism that
keeps the dirty fraction $d$
below $c$ for most of the run. More precisely, the 95th percentile of the dirty
fraction over the run, $p_{95}(d)$, has to satisfy

\begin{equation}
  p_{95}(d) \;\le\; c + \varepsilon
  \label{eq:problem}
\end{equation}

where $\varepsilon$ is a small tolerance for deviations. The threshold should be
set once and while the system is running, the mechanism has to keep the dirty
fraction at this level on its own, so the administrator does not have to adjust
any setting.

\section{Research questions}\label{sec:intro-rqs}

\begin{description}
  \item[RQ1] How can a multi-model transactional system integrate a \emph{hybrid
          mode} that safely adapts between ACID and BASE semantics at runtime,
        when its subsystems hold overlapping resources?

  \item[RQ2] How does the hybrid mode compare with pure ACID and pure BASE
        execution in throughput and inconsistency, and can the inconsistency it
        permits be configured?

  \item[RQ3] Does choosing the mode from the system's own internal metrics
        outperform a fixed ACID/BASE split on the same throughput/inconsistency
        trade-off?
\end{description}

\section{Approach and
  contributions}\label{sec:intro-contributions}\label{sec:intro-approach-overview}

This thesis builds on the simulator of multi-model systems by Zacouris and
Acosta~\cite{zacouris2025m2ts,zacouris2026mxs}. The simulator supports both ACID
and BASE semantics, but only one of them per run. This thesis adds the
following.

\begin{bullets}
  \item[A hybrid execution mode.] The mode is chosen for each transaction
  instead of once for the whole run. Both semantics run side by side on the same
  resources (Section~\ref{sec:approach-hybrid}).

  \item[A shared-resource arbiter.] When ACID and BASE run together, they may
  need the same resource at the same time. The arbiter manages this access, so
  that no resource is corrupted (Section~\ref{sec:approach-arbiter}).

  \item[Two mode oracles.] An oracle chooses the mode of each transaction,
  either ACID or BASE. The adaptive oracle decides from the internal state of
  the system, namely the measured dirty fraction $d$. The fixed-share oracle is
  the alternative. It uses a fixed split between ACID and BASE that is set at
  the start (Section~\ref{sec:approach-oracles}).

  \item[Metrics for hybrid runs.] Additional logs and metrics that compare
  performance and describe the internal state of the system
  (Section~\ref{sec:exp-metrics}).

  \item[An empirical evaluation.] Five parameter sweeps with 620 simulation runs
  in total (Chapter~\ref{chapter:experiments}).
\end{bullets}
