\chapter{Conclusions and Future Work}\label{chapter:conclusion}

This chapter summarises the work, describes the lessons learned from combining
ACID and BASE in one system, and lists open questions for future work.

\section{Summary of the work}\label{sec:concl-summary}

This thesis focused on whether ACID and BASE can run together in one multi-model
system. To address this, the simulator of Zacouris and
Acosta~\cite{zacouris2026mxs} was extended with a hybrid mode, in which a
dedicated mechanism, the \emph{mode oracle}, tags each transaction as ACID or
BASE, and a shared-resource arbiter keeps the two semantics from corrupting each
other's work. We built two mode oracles, an adaptive oracle driven by the dirty
fraction and a fixed-share oracle, and compared their performance.

In the evaluation, the hybrid mode was faster than pure ACID and slower than
pure BASE. The dirty fraction stayed close to the configured critical dirty
threshold, but this held only for a range of workloads, and under constant load
the adaptive oracle did not outperform a fixed split. The hybrid mode therefore
does not make the trade-off between ACID and BASE cheaper, but it allows
different system parameters to be configured.

\section{Lessons learned}\label{sec:concl-lessons}

ACID and BASE cannot simply run side by side, because without a resource
management layer such as the arbiter they corrupt the state of shared
resources.

Sharing resources costs performance in both modes. ACID transactions now
additionally wait on resources that are claimed by BASE or dirty, and BASE
parent transactions wait on ACID locks. As a result, the hybrid mode cannot
reach the throughput of a theoretical combination of ACID and BASE.

Once the resource management layer is in place, any oracle can be used without
changes to the rest of the system, but every value it controls will be paid for
with throughput.

Because the tag is fixed for the whole life of a transaction, transactions
already in flight after a switch push the dirty fraction past the thresholds.
Changing the mode of these transactions would allow more precise control.

\section{Future work}\label{sec:future-work}

\begin{bullets}
  \item[Varying load.] Repeat the oracle comparison under a load that changes
  during a run, where feedback is expected to help most.

  \item[Real multi-model system.] Model the latency and failures of arbiter
  lookups, and validate the hybrid mode against the Vitruvius case studies.

  \item[Stronger statistics.] Run more seeds per cell and a finer grid of fixed
  ACID shares, and count the targets of deferred repairs as dirty.

  \item[Transaction-aware oracle.] Predict how heavy a transaction is from its
  resources and the updates it triggers, and send heavy work to BASE.

  \item[Other oracle policies.] React to the trend of the dirty fraction, read
  it on a fixed time interval, or learn the policy as HybML
  does~\cite{kobus2018htr}.
\end{bullets}
