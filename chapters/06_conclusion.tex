\chapter{Conclusions and Future Work}\label{chapter:conclusion}

This chapter closes the thesis. Section~\ref{sec:concl-summary} summarises the
work. Section~\ref{sec:concl-lessons}
describes the problems that came up when ACID and BASE were combined in one
system, and how they were solved or could be solved.
Section~\ref{sec:future-work} lists the open questions that could be addressed
in future work.

\section{Summary of the work}\label{sec:concl-summary}

This thesis started from the multi-model simulator of Zacouris and
Acosta~\cite{zacouris2026mxs}. The
goal was to combine them in one system that is faster than ACID alone, while the
inconsistency stays within a limit that the administrator sets.

The simulator was extended with a hybrid mode, in which the mode is chosen for
each transaction at admission. A shared-resource arbiter makes both modes
respect each other's work on the same resources, and an oracle chooses the mode.
Two oracles were built, one with a fixed ACID/BASE split and one that reacts to
the measured inconsistency.

Five experiments showed that the hybrid mode lies between the two pure
modes and that its threshold holds within a certain range of workloads. Under
the constant load used here, the adaptive oracle does not beat a well-tuned
fixed split.


In conclusion, the hybrid mode does not make the trade-off between throughput
and inconsistency cheaper, but it makes it configurable with one parameter.
Whether the adaptive oracle pays off under a changing load is still open.

\section{Lessons learned}\label{sec:concl-lessons}

Wrapping the ACID and BASE pipelines is not enough to combine them. As long as
both modes work on the same resources without knowing about each other, the
state of a resource can be corrupted. A resource management layer, such as the
arbiter of this thesis, has to be in place before the modes can be mixed.

An oracle can keep a chosen parameter under control, whether it is the
inconsistency, as in this thesis, or any other value of the system. The main
effect of switching between ACID and BASE, however, is always on the
throughput, so every controlled parameter is paid for with it.

Framing the decision as a single threshold often lets the hybrid mode degrade
to a pure mode. When the threshold is never reached, the run stays in BASE, and
when the system cannot get below it, the run stays in ACID. A policy that learns
from the state of the system, rather than a fixed threshold, could avoid these
cases.

\section{Future work}\label{sec:future-work}

\begin{bullets}
  \item[Varying load.] Repeat the oracle comparison under a load that changes
  during a run, where feedback is expected to help most.

  \item[Real multi-model system.] Model the latency and failures of arbiter
  lookups, and validate the hybrid mode against the Vitruvius case studies.

  \item[Stronger statistics.] Run more seeds per cell and a finer grid of fixed
  ACID shares, and count the targets of deferred repairs as dirty.

  \item[Transaction-aware oracle.] Predict how heavy a transaction is from its
  resources and the updates it triggers, and send heavy work to BASE.

  \item[Other oracle policies.] React to the trend of the dirty fraction, read
  it on a fixed time interval, or learn the policy as HybML
  does~\cite{kobus2018htr}.
\end{bullets}
