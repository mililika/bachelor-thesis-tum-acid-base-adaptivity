\chapter{Experiments}\label{chapter:experiments}

To evaluate the hybrid mode, we ran five experiments on the extended simulator.
Section~\ref{sec:exp-setup} first describes configurations shared by all of
them. First and second experiments answer the question of incosistency threshold
configurability (RQ2), and third experiment answers how does adaptive oracle
pefrormes compared to a static ACID/BASE split (RQ3). Safe adpation between ACID
and BASE (RQ1) is covered only partially by
the experiments, since it is a design question rather than an experimental one.
Foruth and fifth experiments extend the answer to (RQ2) and give further insight into the system,
critical dirty threshold and how well this threshold holds under
different loads. Section~\ref{sec:effective-recovery} takes a closer look at the
recovery threshold.  Section~\ref{sec:exp-threats} closes the chapter with the
threats to validity.

\begin{itemize}
  \item \textbf{X1: Reconciler-processor sweep}
        (Section~\ref{sec:x1-reconciler-sweep}). This experiment varies the
        number of reconciler processors available in the system. It used to
        measure how background reconciliation affects different semantic
        configruations in simulator.

  \item \textbf{X2: Critical dirty fraction threshold sweep}
        (Section~\ref{sec:x2-critical-sweep}). This experiment sweeps the
        critical dirty threshold introduced in this thesis. It tests whether
        this threshold holds, meaning if the measured incosistency fraction
        follows it.

  \item \textbf{X3: Fixed-share oracle ACID/BASE split sweep}
        (Section~\ref{sec:x3-fixed-share-baseline}). This experiment studies how
        the system behaves when a fixed ACID/BASE split is configured at the
        start of the simulation. It compares this with the adaptive oracle,
        where the system chooses ACID or BASE at runtime.

  \item \textbf{X4: Semantic overlap sweep}
        (Section~\ref{sec:x4-overlap-sweep}). This experiment sweeps the
        semantic overlap, which controls how many resources are shared between
        the models.

  \item \textbf{X5: Max number of resources per transaction sweep}
        (Section~\ref{sec:x5-resources-sweep}). This experiment sweeps the
        maximum number of resources a single transaction touches. In this way,
        it controls how many resources, and so how much work, one transaction
        brings.
\end{itemize}

Table~\ref{tab:exp-baseline}. Every experiment starts from it and changes only
the variables it sweeps. Each sweep is crossed with the number of reconciler

default configuration of Zacouris and Acosta~\cite[Table~1]{zacouris2026mxs}.
The deviations from it are listed below the table. Thresholds are given as
fractions in the configuration, while the measured dirty fraction is reported in

\paragraph{Processors.} The reconciler processors are not extra capacity. In
BASE and HYBRID runs the reconcilers are taken out of the 30 foreground
processors, so the IO and CPU processors left for foreground work are 30 minus
the number of reconcilers. Pure ACID runs use no reconcilers and keep all 30.

\paragraph{Workload.}\label{sec:exp-workload} The simulator creates its own
workload, so no external data set is used. The \texttt{EQUILIBRIUM} profile
keeps the number of in-flight transactions constant. Whenever one transaction
finishes, a new one is created at the next step.

\paragraph{Deviations from the reference configuration.} Three new entries were
added to the configuration, the critical dirty threshold, the recovery dirty
threshold and fixed ACID probability. Three values differ from the reference
table.

The only major deviation is the number of simulated seconds was raised from
10\,000\,s to 50\,000\,s. The reason is that switches between \texttt{ACID} and
\texttt{BASE} take time, therefore more simulated time needed to let enough
switches happen for a reliable comparison.

\paragraph{Seeds.} The simulator provides the \emph{transaction-sampling seed}.
It fixes the how many resources each transaction touches, how many models it
reaches, and which models and resources it uses. The same seed also drives the
draws of the fixed-share oracle.

The second seed, the \emph{semantic-overlap seed}, fixes which resources are
shared between the different models. The semantic-overlap seed therefore fixes
the state of the multi-model resource pool.

\paragraph{Experiments implementation.} For each experiment a dedicated runner
script was created. It configures the baseline variables and allows the selected
variable to be swept. Every script is then run under the five seed pairs shared
across all experiments. An experiment provides two types of result, the
fixed-step simulation log and a CSV file in which each row represents one
simulation. A row combines the configuration of that run with the different
output metrics we want to study.

\paragraph{Metrics.}\label{sec:exp-metrics} Three values matter most for the
evaluation.

\begin{bullets}
  \item[Throughput (\texttt{throughput\_tps}).] Root transactions completed per
  second of simulated time. Bookkeepers are not counted.

  \item[$p_{50}$ dirty fraction (\texttt{dirty\_p50\_pct}).] The median share of
  resources that are inconsistent. This describes the typical state of the
  system.

  \item[$p_{95}$ dirty fraction (\texttt{dirty\_p95\_pct}).] The 95th percentile
  of the same quantity. Within one run, inconsistency stays below this value for
  95\% of the simulated time. This describes the bad case, and it is the number
  a threshold is supposed to limit.
\end{bullets}

The resource dirty fraction is sampled at the end of every simulator step, that
is, once per simulated second. We call this value the measured dirty fraction
(also incosistency level), and its 95th percentile is the quantity limited in
Equation~\ref{eq:problem}.

\paperbreak
Two further numbers describe the ACID part of the run.

\begin{bullets}
  \item[ACID time share ($\phi_{\mathrm{time}}$).] How much of the run the
  system spent in ACID mode. The oracle timestamps every decision and sums the
  lengths of the intervals that were marked as ACID

  \item[ACID completed share ($\phi_{\mathrm{comp}}$).] What share of the
  completed transactions were tagged as ACID.
\end{bullets}

and pure BASE in throughput and inconsistency. It is the only sweep in which all
three modes are started under the same conditions.

\paragraph{Experiment configuration.} The sweep covers reconciler processors in

\paragraph{Validation against the base simulator.}\label{sec:x1-validation} The
BASE rows are compared with the received simulator~\cite{zacouris2026mxs} to
check that the pure runs still behave as before. The reference reports that a
few reconcilers push inconsistency up to the semantic overlap, and that more
reconcilers lower inconsistency at the cost of throughput.
Table~\ref{tab:x1-summary} shows the same trade-off. The $p_{50}$ inconsistency
read from Figure~12a of the reference matches ours. With 15 reconcilers, the reference
shows about 18\,\% and our run shows 17.7\,\%. The small differences are most
likely caused by our longer run of 50\,000\,s.

\paragraph{Edge case with zero reconciler processors.} The row with zero
reconcilers looks contradictory at first. Without reconciler processors it
combines a low dirty fraction with a high throughput, which no other row of the
BASE block does. The reason is that repairs are queued on the foreground
processors and run there once the transaction that caused them has
committed~\cite[Section~4.5]{zacouris2026mxs}. So the simulator has two cases.

\begin{bullets}
  \item[No dedicated reconcilers.] Repairs are distributed over all 30
  processors, so the number in flight is bounded by the pool rather than by the
  number of reconcilers.

  \item[Foreground processors converted.] One worker owns one repair until it
  finishes, so no more repairs are in flight at the same time than there are
  reconcilers. Each worker finishes one repair every two seconds, because the
  reconciliation design separates IO and CPU work.
\end{bullets}

\paragraph{Pure ACID/BASE compared to HYBRID.} Figure~\ref{fig:x1-all-modes}
shows that both hybrid configurations lie between pure ACID and pure BASE in
throughput. In runs where the dirty fraction never rises to the critical dirty
threshold, \texttt{HYBRID\_ADAPTIVE} behaves like pure BASE.

\paragraph{Effect of reconciler processors on the fixed-share oracle.} In
Table~\ref{tab:x1-summary}, the small throughput improvement of
\texttt{HYBRID\_FIXED\_SHARE} seems unexpected at first. More reconciler
processors means fewer foreground ones, so the throughput should decrease. What
actually happens is that fewer foreground processors run fewer transactions at
the same time, so fewer ACID transactions hold locks and abort. In addition,
more reconciler processors clear the background work faster, which results in
fewer ACID waits on dirty resources.

\section{X2: Dirty resource fraction threshold
  sweep}\label{sec:x2-critical-sweep}

RQ2 asks whether the hybrid mode with the adaptive oracle makes it possible to
control the inconsistency. X1 answers this question only partially, because it
keeps the critical dirty threshold at 0.10. X2 varies this threshold directly
and checks whether the measured dirty resource fraction follows it.

\paragraph{Experiment configuration.} The experiment covers critical dirty
thresholds of \{0.02, 0.05, 0.10, 0.15, 0.20, 0.30\} and \{1, 5, 10, 15\}
reconciler processors, with all runs in \texttt{HYBRID\_ADAPTIVE}.

The recovery threshold is held at half of the critical dirty threshold,
$r = 0.5c$, which lets the hysteresis band scale with it. A fixed recovery
threshold would cause an error for varying critical dirty fraction, since the simulator only accepts
\texttt{recovery\ threshold} $\le$ \texttt{critical\ dirty\   threshold}.

Runs with reconciler counts outside \{1, 5, 10, 15\} are left out, because X1
shows that the adaptive oracle behaves like pure BASE there.


One detail of this experiment is worth mentioning, which is the semantic overlap
of 0.30. Only 30\,\% of the 5000 resources carry a CPR, so by design a run can be
at most 30\,\% dirty, and this is a hard ceiling on the inconsistency.

Table~\ref{tab:blocking} is the mean time an ACID transaction is blocked, counted
from the moment it meets a dirty or claimed resource that it needs.

\paragraph{The critical dirty threshold sets the inconsistency
  level.}\label{sec:x2-tracking} Table~\ref{tab:x2-tracking} gives the value of
$p_{95}(\mathrm{dirty\ fraction}) - \mathrm{critical\ dirty\ threshold}$,
which is the distance from the configured critical dirty threshold in
percentage points. A positive entry means that $p_{95}(\mathrm{dirty\ fraction})$
overshoots the threshold, and a negative one means that the run stayed below it.

This is the central result of the thesis. The $p_{95}$ dirty fraction is never
more than 1.31 percentage points away from the configured critical dirty
threshold, and the further a run is from the edges of the threshold range, the
smaller this deviation is. In the terms of
Equation~\ref{eq:problem}, the critical dirty threshold works as a configurable
limit on the inconsistency level.

\paragraph{The incosistency deviation changes from overshoot to undershoot.} From
Table~\ref{tab:x2-tracking} we see that the average deviation of $p_{95}$ turns
from positive to negative. It changes direction both when the critical dirty
threshold grows and when more reconciler processors are added.
Figure~\ref{fig:x2-panels} helps to understand the cause. As the critical dirty
threshold grows, more dirty resources are allowed, so ACID transactions wait
longer to be admitted. While the ACID transactions wait, the background work
keeps running. As a result, the foreground of the simulator slows down strongly,
while the reconciler processors keep clearing the dirty resources.

\paragraph{A high number of completed ACID transactions lowers
  throughput.}\label{sec:x2-mechanism} The throughput column of
Table~\ref{tab:x2-grid} is counterintuitive at first. By
Equation~\ref{eq:blocking-probability}, the probability that an ACID transaction
is blocked by at least one dirty resource climbs fast as the critical dirty
threshold increases. A small critical dirty threshold should therefore be the
faster setting. The measurements show the opposite. With 5 or more reconcilers
the runs with a small critical dirty threshold are the slow ones.

The reason is that a small critical dirty threshold forces the system to tag
more transactions as ACID, because it has to keep the inconsistency level low.
The system has to complete more slow work, and as a result the throughput drops
towards pure ACID. As the critical dirty threshold is relaxed, the fraction of
completed transactions tagged ACID drops significantly, because the system can
focus on fast BASE transactions (Figures~\ref{fig:x2-panels}
and~\ref{fig:x2-panels-r1}).

We also see that the time spent in ACID stays almost flat for all runs with five
or more reconciler processors, which is directly related to the mean ACID wait.
The system still spends much time in ACID because each ACID period gets longer,
but most of the throughput comes from completed BASE transactions.

\paragraph{The ACID share can set the inconsistency level.}
Table~\ref{tab:x3-summary} shows how the ACID share and the
number of reconcilers allow inconsistency to be controlled under a static
workload, and the core principles from the previous experiments hold here as
well. The two settings act on different parts of the system.

The ACID share acts on what the system is asked to do. Under
\texttt{EQUILIBRIUM} the number of in-flight transactions is held constant
(Section~\ref{sec:exp-workload}), so increasing the ACID share replaces fast
BASE transactions with slow ACID ones. Throughput falls, fewer transactions are
admitted per second, and less dirtying work enters the system.

The number of reconcilers acts on how fast the dirty set is cleared. More
reconcilers drain the same dirty set faster, so the number of dirty resources is
smaller overall. The rows with one reconciler show
what happens when this second setting is too small to keep up. A single
reconciliation processor is unable to clear the high volume of dirty resources,
which increases the ACID wait time.

Taken together, the share of transactions started as ACID
controls the throughput and the inconsistency of the system, while the number
of reconcilers is an additional setting that controls how fast
the inconsistency is drained.

Consider only the ten close rows, where the nearest
neighbour lies within 12\,\%. In all ten rows the two oracles reach almost the same share of

quantity, which is the ACID share of the completed work. The time spent in ACID mode, however,

\paragraph{One weakness of the adaptive oracle compared to fixed-share.} The
adaptive oracle switches to ACID mode at the moment when the dirty fraction
reaches the critical dirty threshold, which is when the system has already reached
the highest allowed level of inconsistency. The dirtier the system gets, the longer
ACID transactions have to wait. Table~\ref{tab:x3-blocking} shows that at every
reconciler count a larger share of the adaptive ACID transactions is blocked on
a dirty or BASE-claimed resource, and their mean blocked wait is longer. While
fixed-share starts a mix of ACID and BASE transactions at all times, the adaptive oracle
starts all transactions in ACID while the dirty fraction travels from the
critical dirty threshold back down to the recovery threshold. That likely leads
to more ACID transactions in flight at the same time, which compete for locks
and wait on dirty resources.

\paragraph{Implications for a real software system.}
If we know that the workload will be static, we can set the share of
transactions that are started in the slow ACID mode. This increases the throughput compared to pure
ACID while still controlling the inconsistency level of the system.

internal system state, and it performs most of the time better than pure
ACID. It allows the inconsistency to be controlled within a certain range, and if the
tuning effort is acceptable, the fixed-share split between ACID and BASE is
a viable option.

  a fixed split that was tuned for each configuration.

\paragraph{The adaptive oracle does not engage for all semantic
  overlap values.}\label{sec:x4-engagement} Thirteen of the 28 cells in
Table~\ref{tab:x4-overlap} behave exactly like a pure BASE run, because the adaptive oracle
never switches to ACID. The reason is that the semantic overlap sets a hard
ceiling on how much inconsistency is possible by design, while the oracle engages
only where its reading of the dirty fraction reaches the threshold. At a
semantic overlap of 0.10 the ceiling equals the critical dirty threshold of
10\,\%. With one reconciler the dirty
fraction is already pinned near the ceiling, with a $p_{95}$ of 9.62\,\%. In the cells where
the oracle does engage, more semantic overlap raises the background cost of a
transaction. As a result, throughput falls, aborts rise, and the system spends
more time in ACID.

Figure~\ref{fig:x4-overlap-interval} plots the dirty fraction against
semantic overlap, with the configured critical dirty threshold as the dashed
line. In the shaded range from a semantic overlap of 0.20 to 0.30, the $p_{95}$
dirty fraction lands where it was configured. At a semantic overlap of 0.50 the
threshold starts to drift, and as semantic
overlap approaches 1.00 the threshold no longer holds, with a $p_{95}$ of up to
22.51\,\%.

  \centering
  \includegraphics[width=0.76\textwidth]{x4_o10_overlap_band.pdf}
  \captionsetup{format=plain,justification=centering}
  \caption{X4: the measured tail against semantic overlap.}
  \label{fig:x4-overlap-interval}

\paragraph{Why the $p_{95}(dirty\ fraction)$ overshoots the threshold.} The
trigger works, but the limit on $p_{95}$ does not. The oracle still engages
where it was configured to engage, as the column with the reading at the switch
($d_k^{\mathrm{switch}}$) in Table~\ref{tab:x4-overlap} shows. In every
engaged cell of the sweep, the oracle switches to ACID mode just above the
configured critical dirty threshold of 10\,\%.

What breaks the threshold is the work already in flight. A tag is fixed at
admission (Section~\ref{sec:approach-tagging-point}), so a mode switch affects only
the transactions admitted after it and not the 30 that are already running.
Those transactions keep writing, and every write to an overlapped resource
spawns a bookkeeper that inherits the BASE tag of its root. The higher the semantic overlap, the more of this background
work each transaction creates. At a
semantic overlap of 1.00 each transaction has CPR on every resource, so the writes of each root
transaction cascade into bookkeepers that spawn further bookkeepers.

At full overlap this cascade looks endless, but the simulator bounds it
with the bookkeeper depth, which is 5 in every run of this chapter
(Table~\ref{tab:exp-baseline}). A bookkeeper at that depth creates no children,
so each chain stops there.

\FloatBarrier
\findingshead

\begin{bullets}
  \item[O10. The critical dirty threshold does not hold for all semantic overlap values.] The
  oracle needs enough overlap to fire at all. It also needs the overlap to stay
  small enough that one write does not dirty a large share of the resources in
  the background. Figure~\ref{fig:x4-overlap-interval} shows that the critical
  dirty threshold holds only for semantic overlap values from 0.20 to 0.30.
  Below this range every cell is a pure BASE run. Above it, a single write
  reaches so far that the transactions already admitted keep marking resources
  dirty in the background.

  \item[O11. In-flight BASE transactions overflow the critical dirty threshold.]
  The more the models overlap, the more background work every write creates.
  This background work comes from transactions that were tagged BASE before the
  switch, and they keep adding new bookkeepers even after the adaptive oracle
  switches to ACID.
\end{bullets}

transactions wait long and throughput is low, so the reconciler processors clear
more dirty resources in the background and the $p_{95}$ undershoots the critical
dirty threshold.

\findingshead

\begin{bullets}
  \item[O12. Transaction size loads the foreground.] Large transactions take
  much longer to process and collide far more often, so the low throughput comes
  from waiting and from wasted work. Semantic overlap, in contrast, loads the
  reconciler, because BASE resolves bookkeepers with dedicated reconciler
  processors.

  \item[O13. Reconciler processors count decide overshoot or undershoot of incosistency.] The number of
  reconciler processors sets the direction. With few reconciler processors, the
  inconsistency level overshoots, because a switch binds only the transactions
  admitted after it, while the heavy ones already running keep dirtying
  resources. With enough reconciler processors, it undershoots, because heavy
  transactions wait for locks and deliver less work.
\end{bullets}

\paragraph{Why the switch from ACID to BASE undershoots the recovery
  threshold.}\label{sec:recovery-mechanism} This problem was already mentioned in
the previous experiments and in the approach description
(Section~\ref{sec:approach-sampling}), and here we explain it in more detail.
The oracle reads the inconsistency level only once per root transaction, at its
first admission attempt. Under \texttt{EQUILIBRIUM}, a new root transaction is
created only when an in-flight one finishes. In ACID mode, the 30 in-flight
transactions are slow, because they wait for locks and for dirty resources.
While all of them are stuck, no transaction finishes, no new one arrives and no
reading is taken, so between two readings the value the oracle holds is out of
date. The check interval columns in Table~\ref{tab:effective-recovery} show
this, because at every reconciler count the oracle reads less often in ACID mode
than in BASE mode. A reading once per tick would record the exit close to the
recovery threshold, but the first BASE transaction would still be admitted only
when an ACID transaction finishes (Section~\ref{sec:approach-sampling}).

\section{Threats to validity}\label{sec:exp-threats}

The results above hold under the conditions of this chapter. The following
points limit how far they can be generalised.

\begin{bullets}
  \item[Stationary load only.] Every run uses the \texttt{EQUILIBRIUM} profile,
  so the load never changes (Section~\ref{sec:approach-stationary-load}). This
  is the setting in which feedback helps least.

  \item[Simulated execution.] The simulator treats all models as one entity, so
  a lookup of the arbiter has no latency and never fails
  (Section~\ref{sec:approach-arbiter-lookup}).

  \item[Five seeds per cell.] The results move little between seeds, but five
  runs give an indication rather than a confidence interval.

  \item[Hidden dirty resources.] A deferred repair is not in the dirty set until
  it is created (Section~\ref{sec:approach-arbiter}). The measured dirty
  fraction can therefore be lower than the real inconsistency, most of all in
  ACID mode.

  \item[Interpolated X3 comparison.] The fixed-share oracle is sampled at five
  values of the ACID share. Table~\ref{tab:x3-matched} reads its throughput
  between measured points, and some of these points are far apart.
\end{bullets}
