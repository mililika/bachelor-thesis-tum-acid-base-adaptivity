\chapter{Experiments}\label{chapter:experiments}

To evaluate the hybrid mode, we ran five experiments on the extended simulator.
Section~\ref{sec:exp-setup} first describes the setup that all of them share.
X1 and X2 answer RQ2, and X3 answers RQ3. RQ1 is covered only partially by the
experiments, since it is a design question rather than an experimental one. It
is answered in Chapter~\ref{chapter:approach}, which defines a safe system and
argues why the design achieves it. The experiments add only weak evidence for
it (O1). X4 and X5 extend the answer to RQ2. They give further insight into the
system, into the critical dirty threshold $c$, and into how well $c$ holds under
different loads. Section~\ref{sec:effective-recovery} reports no new runs. It
takes a closer look at the X2 runs and shows where the oracle returns to BASE.
Section~\ref{sec:exp-summary} closes the chapter and maps the findings to the
research questions.

\begin{itemize}
  \item \textbf{X1: Reconciler-processor sweep}
        (Section~\ref{sec:x1-reconciler-sweep}). This experiment varies the
        number of reconciler processors available in the system. It runs
        simulations in four configurations. These are \texttt{ACID},
        \texttt{BASE}, \texttt{HYBRID\_ADAPTIVE} and
        \texttt{HYBRID\_FIXED\_SHARE}.

  \item \textbf{X2: Dirty resource fraction threshold sweep}
        (Section~\ref{sec:x2-critical-sweep}). This experiment sweeps the
        critical dirty threshold $c$ introduced in this thesis. It tests whether
        $c$ really works as a threshold, that is, whether the measured dirty
        fraction follows it.

  \item \textbf{X3: Fixed-share oracle ACID/BASE split sweep}
        (Section~\ref{sec:x3-fixed-share-baseline}). This experiment studies how
        the system behaves when a fixed ACID/BASE split is configured at the
        start of the simulation. It compares this with the adaptive oracle, where
        the system chooses ACID or BASE at runtime.

  \item \textbf{X4: Semantic overlap sweep}
        (Section~\ref{sec:x4-overlap-sweep}). This experiment sweeps the
        semantic overlap $\sigma$, which controls how many resources are shared
        between the models. This in turn controls how many child transactions
        are created.

  \item \textbf{X5: Max number of resources per transaction sweep}
        (Section~\ref{sec:x5-resources-sweep}). This experiment sweeps $L$, the
        maximum number of resources a single transaction touches. In this way,
        it controls how many resources, and so how much work, one transaction
        brings.
\end{itemize}



\section{Experimental setup}\label{sec:exp-setup}

This section shows the baseline simulator configuration, described in
Table~\ref{tab:exp-baseline}. Every experiment starts from it and changes only
the variables it sweeps. Each sweep is crossed with the reconciler count $R$,
which X1 sweeps on its own. X2 also sets $r = 0.5c$, and X3 sweeps the fixed
ACID share $p_{\mathrm{acid}}$. Most settings come from the table of simulation
parameters and default configuration of Zacouris and
Acosta~\cite[Table~1]{zacouris2026mxs}. The deviations from it are listed below
the table. Thresholds are given as fractions in the configuration, while the
measured dirty fraction is reported in percent.

\paragraph{Processors.} The reconciler count $R$ is not extra capacity. In BASE
and HYBRID runs the $R$ reconcilers are taken out of the 30 main processors, so
$30 - R$ IO and CPU processors are left for foreground work. Pure ACID runs use
no reconcilers and keep all 30. X1 discusses this rule in more detail
(Section~\ref{sec:x1-reconciler-sweep}).

\paragraph{Workload.}\label{sec:exp-workload} The simulator creates its own
workload, so no external data set is used. The \texttt{EQUILIBRIUM} profile
keeps the number of in-flight transactions constant. Whenever one transaction
finishes, a new one is created at the next step. In HYBRID runs the new
transaction may still wait for admission. The load is therefore stationary by
design. This allows the throughput to be compared across different experiment
configurations, but it also means the mode oracles are never tested under a more
real-world setup. The simulator provides an alternative profile,
\texttt{TERMINAL}, which could give more insight into the usefulness of
adaptivity. Unfortunately it was still under construction during this thesis, so
it was left for future work.

\paragraph{Deviations from the reference configuration.} Two new entries were
added to the configuration, the critical dirty threshold $c$ and the recovery
dirty threshold $r$. Both are needed by the adaptive oracle. A third new entry,
$p_{\mathrm{acid}}$, is needed by the fixed-share oracle. Three values differ
from the reference table. First, the number of simulated seconds was raised
from 10\,000\,s to 50\,000\,s. The reason is that switches between \texttt{ACID}
and \texttt{BASE} take time. More simulated time is therefore needed to let
enough switches happen for a reliable comparison. Second, the reference uses
one reconciliation processor by default, while here $R$ is part of every sweep.
Third, the reference table has no entry for the number of models one
transaction reaches. It is set to 4 here.

\paragraph{Seeds.} The simulator provides the \emph{transaction-sampling seed}.
It fixes the sequence of generated transactions for a given configuration, that
is, how many resources each transaction touches, how many models it reaches, and
which models and resources it uses. The same seed also drives the draws of the
fixed-share oracle. The second seed, the \emph{semantic-overlap seed}, fixes
which resources are shared between the different models. The semantic-overlap
seed therefore fixes the state of the multi-model resource pool. Both seeds
together make every run fully reproducible. The same five pairs of seeds are
used for every one of the five experiments. Runs with different settings still
see different transactions once their timing differs, and X5 changes the size
distribution itself.

\paragraph{Experiments implementation.} For each experiment a dedicated runner
script was created. It configures the baseline variables and allows the selected
variable to be swept. Every script is then run under the five seed pairs shared
across all experiments. An experiment provides two types of result, the
fixed-step simulation log and a CSV file in which each row represents one
simulation. A row combines the configuration of that run with the different
output metrics we want to study. The output of a full sweep over the five seeds
is one further CSV file, which averages the values of the separate CSV files.
These averaged results are the ones used in the experiment data tables. Every
cell is the mean over the five seeds. Percentiles are computed per run first and
then averaged, so they are not percentiles of the pooled samples.

\paragraph{Spread across seeds.} The seeds move the results very little. For
the adaptive oracle the seed standard deviation of $p_{95}$ is between 0.02 and
0.19 percentage points in every engaged cell of X2, and the standard deviation
of throughput is at most 3.3\,\% of the mean. The fixed-share oracle of X3 is
noisier. The median coefficient of variation of its $p_{95}$ is 8.6\,\%, against
0.7\,\% for the adaptive oracle.

\paragraph{Warm-up.} The runners define a warm-up window of 5000\,s, one tenth
of the run. It is applied only to two steady-state columns of the CSV files,
which are not used in this chapter. All reported values, including the
percentiles, throughput and switch counts, cover the whole run with the first
5000\,s. The effect on the percentiles is small. It is at most about 0.1
percentage points. For example, at $R = 1$ the adaptive $p_{95}$ is 10.47\,\%
over the whole run and 10.38\,\% without the warm-up.

\paragraph{Metrics.}\label{sec:exp-metrics} Three values matter most for the
evaluation.

\begin{bullets}
  \item[Throughput (\texttt{throughput\_tps}).] Root transactions completed per
  second of simulated time. Bookkeepers are not counted. This is the
  performance side.

  \item[$p_{50}$ dirty fraction (\texttt{dirty\_p50\_pct}).] The median share of
  resources that are inconsistent. This describes the typical state of the
  system.

  \item[$p_{95}$ dirty fraction (\texttt{dirty\_p95\_pct}).] The 95th percentile
  of the same quantity. Within one run, inconsistency stays below this value
  for 95\% of the simulated time. This describes the bad case, and it is the
  number a threshold is supposed to bound.
\end{bullets}

The resource dirty fraction is sampled at the end of every simulator step, that
is, once per simulated second. We write $d$ for this measured value and
$p_{95}(d)$ for its 95th percentile, as in Equation~\ref{eq:problem}. The oracle
takes its own reading $d_k$ only when it admits a root transaction
(Section~\ref{sec:approach-sampling}). The two are kept apart, because the
reading of the oracle is part of the system under study, while $d$ is the
measurement. Additionally, pure ACID runs have no dirty-fraction data at all,
because they hold no inconsistency by design. Those cells read ``n/a by
construction''.

\paperbreak
Two further numbers describe the ACID part of the run.

\begin{bullets}
  \item[$\phi_{\mathrm{time}}$ (\texttt{acid\_fraction\_time}).] How much of the
  run the system spent in ACID mode. The oracle timestamps every decision and
  sums the lengths of the intervals that were marked as ACID.

  \item[$\phi_{\mathrm{comp}}$ (\texttt{acid\_fraction\_completed}).] What share
  of the completed transactions were tagged as ACID.
\end{bullets}

Bookkeeper transactions are not counted in $\phi_{\mathrm{comp}}$. They inherit
the mode of the root transaction, so counting them would weight each mode by how
many repairs it happened to trigger rather than by the work that was actually
submitted.

The meaning of $\phi_{\mathrm{time}}$ depends on the oracle. Pure ACID runs set
it to 1 and pure BASE runs to 0. The adaptive oracle adds the time during which
its global mode is ACID. The fixed-share oracle has no global mode. It adds the
time after each admission whose draw was ACID, until the next admission. The
values of the two oracles are therefore not the same quantity.

\paperbreak
The remaining columns of the tables are defined once here.

\begin{bullets}
  \item[$p_{99}$ dirty fraction.] The 99th percentile of $d$, computed like
  $p_{95}$.

  \item[Switches.] How often the adaptive oracle changes the mode during the
  run. A cell with zero switches is degenerate. For the fixed-share oracle the
  column counts changes between two consecutive draws, which is not comparable
  with the adaptive count.

  \item[Latency (\texttt{txn\_latency\_mean\_ms}).] The mean time from the
  creation of a root transaction to its commit.

  \item[Aborts.] The share of finished attempts that aborted, that is, aborts
  divided by aborts plus completed transactions. Every abort in this chapter is
  an ACID abort, since BASE transactions never abort.

  \item[$\mathrm{ACID}_{\mathrm{cmt}}$, $\mathrm{BASE}_{\mathrm{cmt}}$.]
  Committed root transactions tagged ACID and BASE.

  \item[Adm.\ $A$ and blocked share.] Adm.\ $A$ counts the admitted ACID root
  transactions. The blocked share is the part of them that waited at least once
  on a dirty or BASE-claimed resource.

  \item[Mean ACID wait.] The mean length of one such wait episode.
\end{bullets}

The working tolerance $\varepsilon$ of Equation~\ref{eq:problem} is 1.5
percentage points. This is the largest deviation measured in X2
(Section~\ref{sec:x2-tracking}).


\section{X1: Reconciler-processor sweep}\label{sec:x1-reconciler-sweep}

X1 answers the first part of RQ2, how the hybrid mode compares with pure ACID
and pure BASE in throughput and inconsistency. It is the only sweep in which all
three modes are started under the same conditions.

\paragraph{Experiment configuration.} The sweep covers $R \in
  \{0,1,5,10,15,20,25\}$ for four configurations, pure ACID, pure BASE,
\texttt{HYBRID\_ADAPTIVE} and \texttt{HYBRID\_FIXED\_SHARE}, with five seeds,
so 140 runs in total. The fixed-share oracle runs at $p_{\mathrm{acid}} = 0.5$,
so it starts every second transaction in ACID. Everything else is at the
baseline of Table~\ref{tab:exp-baseline}.

Table~\ref{tab:x1-summary} reports one row per configuration and reconciler
count. Its columns are defined in Section~\ref{sec:exp-metrics}. ACID gets a
single row for all seven reconciler values, since reconciler processors by
design have no influence in pure ACID mode.

\paragraph{Processors configuration rule.} The base
simulator~\cite{zacouris2026mxs} is constructed in a way that the reconciler
count (\texttt{numberOfReconcilerProcessors}) does not add background compute.
It says how many of the main processors are used for reconciliation
(Section~\ref{sec:exp-setup}). For example, with $N_{\mathrm{processors}} = 30$
and $R = 5$, we actually get 25 IO/CPU processors and 5 reconcilers. At the top
of the sweep only 5 foreground processors are left. This shows the trade-off
between foreground and background work.

\paragraph{Validation against the base simulator.}\label{sec:x1-validation} The
ACID and BASE semantics are inherited from the received
simulator~\cite{zacouris2026mxs}. As a first step we compare our BASE rows with
the ones reported there. This shows that the pure runs are untouched and still
work appropriately.

The trade-off reproduces. The reference reports that a single reconciler lifts
throughput above the $R = 0$ baseline, that few reconcilers push inconsistency
up to the level set by the semantic overlap, and that further reconcilers bring
inconsistency back down at the cost of throughput. Table~\ref{tab:x1-summary}
shows the same shape. At $R = 1$: inconsistency reaches $29.50\,\%$ against an
overlap of 30\,\%. From there both curves fall together, and they keep falling
up to $R = 25$, where only 5 foreground processors are left.

One claim does not reproduce exactly. The reference has throughput falling
below its $R = 0$ baseline once ten or more reconcilers are used, while here
the drop sits between $R = 15$ and $R = 20$. The size of the mismatch can be
read from the relative throughput. Read from Figure~12a of the reference, $R =
1$ gives about 1.35 times the baseline and $R = 25$ about 0.4 times. Here $R =
1$ gives 1.98 times and $R = 25$ gives 0.34 times. For $R \ge 1$ our BASE
throughput is almost exactly linear in the foreground processors, with 0.133
tps for each of them. The crossing point is therefore fixed by the $R = 0$
value, $1.954 / 0.133 = 14.6$ foreground processors, that is $R \approx 15.4$.
So the gap lies in the $R = 0$ baseline, which is lower relative to the other
rows than in the reference. The cause is not tested. The run duration, 50\,000\,s here against
10\,000\,s there (Section~\ref{sec:exp-setup}), and the different seeds are
possible reasons.

\paragraph{Explanation of $R = 0$ edge case.} The $R = 0$ row looks
contradictory at first. With no reconciler processors it combines a low dirty
fraction with a high throughput, which no other row of the BASE block does. The
reason is that repairs are queued on the foreground processors and run there
once the transaction that caused them has committed~\cite[Section~4.5]{zacouris2026mxs}.
So the simulator has two cases.

\begin{bullets}
  \item[No dedicated reconcilers ($R = 0$).] Repairs are distributed over all 30
  processors, so the number in flight is bounded by the pool rather than by $R$.

  \item[Foreground processors converted ($R \ge 1$).] One worker owns one repair
  until it finishes, so at most $R$ repairs are in flight at the same time. Each
  worker finishes one repair every two seconds, because the reconciliation
  design separates IO and CPU work.
\end{bullets}

Repair at $R = 0$ is therefore faster and the dirty fraction stays low.
Throughput is still not the highest. No processors are lost, but foreground and
repair work share one pool.

\paragraph{Pure ACID/BASE compared to HYBRID.} Table~\ref{tab:x1-summary} shows
that both hybrid configurations take the middle ground between pure ACID and
pure BASE. O3 below discusses this in detail.
\texttt{HYBRID\_FIXED\_SHARE} has low levels of inconsistency, which can be
explained by the amount of time it spends in the slow ACID mode. Its throughput
rises slightly with the number of reconciliation processors, from 0.084 to
0.099 tps. Figure~\ref{fig:x1-all-modes} puts all four configurations on one
log-scale axis, so the order between them can be read directly.

\paragraph{Why fixed-share gains throughput at high $R$.} From
Table~\ref{tab:x1-summary} we notice that the small throughput improvement of
\texttt{HYBRID\_FIXED\_SHARE} at first seems unexpected. An increase of
reconciler processors decreases the number of foreground ones, so it should
decrease the throughput. What actually happens is that fewer foreground
processors run fewer transactions at the same time, so fewer ACID transactions
hold locks and abort. Every abort in this sweep is an ACID abort, since BASE
transactions never abort. Counted per completed ACID transaction, the aborts
stay flat over most of the sweep and then fall away at the end. At $R = 15$:
1.50 aborts. At $R = 20$: 0.48 aborts. At $R = 25$: 0.06 aborts. Additionally,
the resources in the background are cleared faster, which leads to fewer
collisions and less waiting on dirty resources. The number of ACID transactions
that block on a dirty resource follows the same direction. At $R = 5$: 425
blocked. At $R = 25$: 110 blocked.

\findingshead

\begin{bullets}
  \item[O1. None of the runs stall.] Every one of the 140 runs makes progress
  and no run ends with a transaction in the blocked queue. This gives a weak
  argument for RQ1, showing that in 50\,000\,s no deadlock was encountered.

  \item[O2. The oracle engages for $1 \le R \le 15$.]
  At $R = 0$ and $R = 25$ every adaptive run degenerates to pure BASE. The
  adaptive oracle prefers BASE and starts there. So in runs where the
  inconsistency fraction never reaches the configured threshold, the oracle
  never engages. $R = 20$ is near-degenerate. Only 2 of the 5 seeds switch at
  all, with 2.4 switches on average, and the other three are identical to pure
  BASE. The $R = 20$ row of Table~\ref{tab:x1-summary} therefore shows almost
  the same values for the BASE and the adaptive modes. Throughput of both modes
  is compared in Figure~\ref{fig:x1-throughput-valley}.

  \item[O3. Hybrid throughput lands between ACID and BASE.]
  For \texttt{HYBRID\_ADAPTIVE} at $R = 1$ to $15$ throughput falls far below
  pure BASE, as Figure~\ref{fig:x1-all-modes} shows. At $R = 15$: 0.419 tps
  against 2.001 tps. Against pure ACID the same runs are ahead everywhere. In
  absolute tps the adaptive oracle stays closer to ACID and buys back only part of
  the throughput that BASE offers. On the log scale of
  Figure~\ref{fig:x1-all-modes} it sits below the middle at $R = 1$ and $R = 5$,
  and slightly above it at $R = 10$ and $R = 15$. The fixed-share
  throughput is nearly flat over the same range, which indicates that the
  throughput valley we see in Figure~\ref{fig:x1-throughput-valley} comes from
  the adaptive oracle reacting to levels of inconsistency. Throughput does not
  simply follow the time spent in ACID across the two oracles. At $R = 1$ the
  fixed-share oracle spends more time in ACID than the adaptive one and is still
  faster.

  \item[O4. The configured threshold bounds inconsistency.]
  With $c$ held at 0.10 the adaptive $p_{95}$ never rises more than 0.62
  percentage points above it at any engaged $R$. It is the adaptive oracle that
  keeps the dirty fraction limited, but the bound is not hard, since $p_{99}$
  reaches 11.9\,\%. The threshold $c$ caps the tail rather than sets the level.
  At $R = 10$ and $R = 15$ the median runs far below it, at 0.17\,\% and
  0.02\,\%. At $R = 1$ and $R = 5$ the median is closer, at 5.73\,\% and
  3.00\,\%. Figure~\ref{fig:x1-tail-bound} draws the spread against $c$.
\end{bullets}

O1 gives weak evidence for RQ1. O2 to O4 answer the first part of RQ2 for $c =
  0.10$. The adaptive hybrid mode is faster than pure ACID and slower than pure
BASE, and its $p_{95}$ stays near the configured $c$.

\section{X2: Dirty resource fraction threshold
  sweep}\label{sec:x2-critical-sweep}

RQ2 asks whether the hybrid mode with the adaptive oracle allows the
inconsistency to be controlled. X1 answers that question partially, but it holds
the critical threshold at $c = 0.10$. X2 varies $c$ directly and checks whether
the measured dirty resource fraction follows it.

\paragraph{Experiment configuration.} The grid covers $c \in \{0.02, 0.05, 0.10,
  0.15, 0.20, 0.30\}$ against $R \in \{1, 5, 10, 15\}$ with five seeds, so 120
runs in total, all \texttt{HYBRID\_ADAPTIVE}. The recovery threshold is held at
$r = 0.5c$, which lets the hysteresis band scale with $c$. Otherwise we could
configure values like $c = 0.02$ and $r = 0.05$, which the simulator rejects as
an error.

The values $R \in \{0, 20, 25\}$ are left out, because X1 shows that the
adaptive oracle degrades to BASE at $R = 0$ and $R = 25$ and is near-degenerate
at $R = 20$.

One detail of this experiment is important. It is the semantic overlap
$\sigma$, configured to $\sigma = 0.30$. So only 30\,\% of the 5000 resources
carry a CPR and the rest can never be dirty. That gives a hard ceiling on how inconsistent
the system can become. A run can be at most 30\,\% dirty.

Table~\ref{tab:x2-grid} gives every cell of the sweep with its throughput,
measured $p_{95}$ dirty fraction and mode-switch count. A cell marked ``deg.''
is degenerate. There the dirty resource fraction never reaches the configured
threshold $c$, so all runs of that cell are pure BASE without a single mode
switch.

\paragraph{The critical dirty threshold $c$ sets the inconsistency
  level.}\label{sec:x2-tracking} Table~\ref{tab:x2-tracking} gives the same
$p_{95}$ column as its distance from the configured $c$, in percentage points
and averaged over the five seeds. A positive entry means the $p_{95}$ overshoots
the threshold $c$, and a negative one means the run stayed under it.

This is the central result of the thesis. The threshold is varied from 2\,\% to
30\,\% and the reconciler count from 1 to 15, and in every cell where the oracle
engages the measured $p_{95}$ is at most 1.5 percentage points away from the
configured $c$. That holds in each of the 95 engaged runs and not only in the
means. The largest single deviation is $+1.50$\,pp. At $c = 0.10$ the twenty
individual runs land between 9.10\,\% and 10.72\,\%. These deviations are much
larger than the seed spread. The seed standard deviation of $p_{95}$ lies
between 0.02 and 0.19 percentage points in every engaged cell. In the terms of
Equation~\ref{eq:problem}, $c$ behaves as a configurable threshold on the
inconsistency level.

\paragraph{The deviation from the threshold is two-sided.} Reading
Table~\ref{tab:x2-tracking} we see that the averaged $p_{95}$ turns from a
positive to a negative value as $R$ grows, and the same happens as the critical
dirty threshold $c$ grows. The following explanation is an interpretation of
the data, not a measured cause. The switch into ACID is not late. At $c =
  0.10$ the oracle enters ACID at a median reading of 10.10 to 10.14\,\% at every
$R$ (Section~\ref{sec:effective-recovery}). The sign change more likely comes
from what happens after the switch. The transactions already in flight keep
their BASE tag and keep dirtying resources, so the dirty fraction overshoots
$c$ for a while. At $c = 0.10$ the highest dirty fraction of a run reaches
13.3\,\% at $R = 1$ and 11.5\,\% at $R = 15$. The reconcilers then drain the
dirty set down to $r$. With few reconcilers the overshoot lasts long and pushes
the run above $c$. With many reconcilers the overshoot is short, the drain is
fast, and the run lands below. The trend with $c$ fits the hysteresis band.
Since $r = 0.5c$, a larger $c$ also gives a wider band below $c$, so a larger
part of each cycle is spent under the threshold. At $c = 0.02$ the band is 1
percentage point wide. At $c = 0.20$ it is 10 percentage points wide. What an operator can rely on is
therefore a magnitude. It is $|p_{95} - c| \le 1.5$\,pp.

\paragraph{A high number of ACID transactions lowers
  throughput.}\label{sec:x2-mechanism} The throughput column of
Table~\ref{tab:x2-grid} is surprising at first. A transaction touches up to $L =
  50$ resources, so by Equation~\ref{eq:blocking-probability} its chance of
meeting at least one dirty resource, and waiting on it, climbs fast with the
dirty fraction. A small critical threshold $c$ should therefore be the faster
setting, since an ACID transaction can start its work without that wait. The
measurements show a different reality. For $R \ge 5$ the runs with a small value
of $c$ are the slow ones. $R = 1$ behaves differently and is discussed at the
end of this part.

The reason is that a small $c$ forces the system to tag more transactions as
ACID, because it has to keep the inconsistency level low. As a result the
throughput drops towards pure ACID, which gives 0.0418\,tps. The small-$c$
cells are still well above it. At $c = 0.02$ and $R = 5$: 0.1885\,tps. The
throughput differences between the cells are far larger than the seed spread,
which is at most 3.3\,\% of the mean.
Table~\ref{tab:blocking} adds the metrics that show this. They are the number of
admitted ACID transactions, the mean ACID wait, the committed counts of ACID and
BASE transactions, and the mean transaction latency from creation to commit. As
in the previous experiments, all values are averaged across the five seeds.

Figures~\ref{fig:x2-panels-r1-top} to~\ref{fig:x2-panels-bottom} plot the same
metrics against $c$, with three panels each. Figures~\ref{fig:x2-panels-r1-top}
and~\ref{fig:x2-panels-top} show the mean ACID wait, the ACID admissions and
$\phi_{\mathrm{time}}$. Figures~\ref{fig:x2-panels-r1-bottom}
and~\ref{fig:x2-panels-bottom} show $\phi_{\mathrm{comp}}$, the BASE commits and
the throughput. The first two are for $R = 1$. The last two have one line for
each of $R = 5$, 10 and 15.

Table~\ref{tab:blocking} and Figures~\ref{fig:x2-panels-top}
and~\ref{fig:x2-panels-bottom} show two further details. The mean ACID wait
grows with the dirty fraction threshold, because more resources are allowed to
be dirty, so ACID transactions wait longer on dirty or BASE-claimed resources.
At the same time the share of completed ACID transactions $\phi_{\mathrm{comp}}$
drops sharply. At $R = 5$ and $R = 10$ $\phi_{\mathrm{time}}$ stays almost the
same, and at $R = 15$ it falls only slightly, from 0.170 to 0.130. Relaxing the
allowed inconsistency lets more BASE transactions commit, but the time spent in
ACID does not fall. The likely reason is that $\phi_{\mathrm{time}}$ is set by
how long each ACID visit takes to drain the dirty set from $c$ to $r$, and not
by how many ACID transactions are admitted. The mean lock time also falls as $c$
grows. At $R = 5$ and $c = 0.02$: 2.6\,s. At $R = 5$ and $c = 0.20$: 0.6\,s.

A further insight is that the mean transaction latency falls as $R$ grows,
although fewer foreground processors are left. The most likely reason is that
more reconcilers clear the dirty resources faster. ACID transactions then wait
less, and the system spends less of the run in ACID, so more of the committed
transactions are fast BASE ones. The time until a dirty resource is cleared is a
different metric and is not shown in the table. It falls with $R$ as well, but it
rises with $c$. At $R = 1$: from 173\,s at $c = 0.02$ to 991\,s at $c = 0.20$.

At $R = 1$ the picture is different (Figures~\ref{fig:x2-panels-r1-top}
and~\ref{fig:x2-panels-r1-bottom}). Throughput is U-shaped in $c$. At $c =
  0.02$: 0.0907\,tps. At $c = 0.10$: 0.0711\,tps. At $c = 0.20$: 0.0908\,tps.
Here $\phi_{\mathrm{time}}$ does fall, from 0.696 to 0.372. A single reconciler
drains the dirty set slowly, so every ACID visit is long and every ACID
transaction waits long. ACID admissions fall from 2633 to 253 and ACID commits
from 2162 to 218, while BASE commits rise from 2371 to 4321. In between, BASE
commits grow more slowly than ACID commits disappear. At $c = 0.10$: 434 ACID
and 3123 BASE commits. Throughput therefore first falls, and it returns to its
$c = 0.02$ level only at $c = 0.20$.

\findingshead

\begin{bullets}
  \item[O5. The threshold $c$ controls inconsistency.]
  The measured $p_{95}$ dirty fraction is at most 1.5 percentage points away
  from the configured $c$ in every engaged cell of the sweep, as
  Table~\ref{tab:x2-tracking} lists cell by cell. That answers the part of RQ2
  about the configurability of inconsistency. The deviation is two-sided. A
  small value of $c$ overshoots and a high value undershoots. Under
  Equation~\ref{eq:problem} only the overshoot counts against the bound, and it
  stays within $\varepsilon = 1.5$\,pp.

  \item[O6. A high $c$ switches the oracle off.] O5 holds only while the oracle
  actually engages. It stops engaging once the inconsistency that BASE
  produces on its own stays below the configured threshold $c$. Those are the
  cells marked ``deg.'' in Table~\ref{tab:x2-grid}. The configurable range of
  RQ2 therefore has an upper limit, which is set by how dirty the system becomes
  on its own. That limit is set by the semantic overlap $\sigma$ and by $R$
  together. Pure BASE reaches a $p_{95}$ of 29.6\,\% at $R = 1$ but only
  18.5\,\% at $R = 15$, so $R = 15$ is already degenerate at $c = 0.20$. A lower
  $\sigma$ caps the dirty fraction earlier, so the oracle switches off at a
  lower $c$.

  \item[O7. A higher $c$ moves work from ACID to BASE.]
  For $R \ge 5$, raising the critical threshold $c$ makes ACID work slower. It
  admits fewer ACID transactions and makes each one wait longer
  (Table~\ref{tab:blocking}), because more of the system is dirty when they
  run. $\phi_{\mathrm{time}}$ barely moves while $\phi_{\mathrm{comp}}$
  collapses (Figures~\ref{fig:x2-panels-top} and~\ref{fig:x2-panels-bottom}).
  The extra throughput is BASE work done inside the BASE time the run already
  had. What frees it is likely the locks the missing ACID transactions no longer
  hold. The mean lock time falls as $c$ grows, which fits this reading, but no
  metric measures the freed locks directly. At $R = 1$ the exchange is weaker and throughput is U-shaped.
\end{bullets}

\section{X3: Fixed-share oracle ACID/BASE split
  sweep}\label{sec:x3-fixed-share-baseline}

The fixed-share oracle (Section~\ref{sec:approach-fixed-share-oracle}) allows
users to set the probability of starting a transaction in ACID mode,
$p_{\mathrm{acid}}$, and by configuration $p_{\mathrm{base}} = 1 -
  p_{\mathrm{acid}}$. It was introduced to give a comparison ground for the
adaptive oracle, which makes its decision from the internal system state by
reading the dirty fraction $d_k$ at admission. In fixed-share we set the split
value at the beginning and the system afterwards uses no internal state
information. X3 answers RQ3. We want to understand whether the adaptive oracle
performs better than a split decided at the start. The fixed-share oracle is the
ablation baseline of Section~\ref{sec:approach-fixed-share-oracle}. It uses the
same hybrid machinery with only the feedback signal removed.

\paragraph{Experiment configuration.} The ACID share $p_{\mathrm{acid}}$ takes
the values 0.05, 0.10, 0.15, 0.25 and 0.50. Each of them is run against $R \in
  \{1, 5, 10, 15\}$, with five seeds per cell. That gives 100 runs, with everything else at the baseline of
Table~\ref{tab:exp-baseline}. The $p_{\mathrm{acid}} = 0.50$ rows are the same
runs as the fixed-share rows of X1 at the same $R$, so 20 of the 100 runs repeat
X1. The Switch.\ column of Table~\ref{tab:x3-summary} counts changes between
two consecutive draws and cannot be compared with the switches of the adaptive
oracle (Section~\ref{sec:exp-metrics}).

Every run in this thesis is executed under \texttt{EQUILIBRIUM}, a stationary
load (Section~\ref{sec:exp-workload}). The intended scenario for the adaptive
oracle is a varying load, where it can adapt to incoming changes. The comparison
below is therefore run in a configuration that is not ideal for the adaptive
oracle.

\paragraph{The pair $(p_{\mathrm{acid}}, R)$ sets the inconsistency level.}
Table~\ref{tab:x3-summary} gives useful insight into how $p_{\mathrm{acid}}$ and
$R$ allow inconsistency to be controlled under a static workload, and the core
principles from the previous experiments hold here as well. The two settings
work on different parts of the system.

The share $p_{\mathrm{acid}}$ works on what the system is asked to do. Under
\texttt{EQUILIBRIUM} the in-flight transactions are held constant
(Section~\ref{sec:exp-workload}), so increasing the $p_{\mathrm{acid}}$ share
replaces fast BASE transactions with slow ACID ones. Throughput falls, fewer
transactions are admitted per second, and less dirtying work enters the system.
That is what we see in the cases with $R \ge 5$, where a $p_{\mathrm{acid}}$
increase drops the throughput but drops the inconsistency level as well. At $R
  = 1$ the inconsistency level also falls, from 21.73\,\% to 3.10\,\%, but
throughput does not fall steadily.

$R$ works on a different part. Reconcilers do not change what is submitted or
how many resources are marked as dirty. They decide how fast the dirty set is
cleared, so a higher $R$ drains the same dirtying rate faster and holds a
smaller dirty set overall. The $R = 1$ column shows what happens when that
second setting is too small to keep up. One single reconciliation processor is
unable to clear the high volume of dirty resources, which increases the ACID
wait time. With an increase of the ACID share $\phi_{\mathrm{time}}$ grows, as
it does at every $R$. As a result, the more ACID transactions we have in flight,
the higher the chance of waits and aborts.

Taken together, by controlling how many transactions should be completed as ACID
we can control the throughput or the inconsistency of the system, and $R$ gives
an additional setting, which allows us to control how fast the inconsistency
will be drained. This is the common ground that makes the fixed-share and the
adaptive oracle comparable at all, because it allows us to match settings under
the two oracles by inconsistency level and compare their throughput.


\paragraph{Matching inconsistency for throughput
  comparison.}\label{sec:x3-frontier} The two oracles are configured in
different ways. By setting $c = 0.10$ we configure the adaptive oracle to
limit inconsistency near 10\,\%. Setting $p_{\mathrm{acid}} = 0.10$ makes the
fixed-share oracle start one transaction in ten in ACID mode. There is no pair
of settings that makes the two runs comparable by configuration, so the match
is made on inconsistency, as the output of the runs.

An exact match rarely exists, because the fixed-share experiment was swept at
only five probabilities. Table~\ref{tab:x3-matched} groups all adaptive and
fixed-share runs under the same $R$. The adaptive runs are the X2 sweep of the
threshold $c$, given in Table~\ref{tab:x2-grid}, and the fixed-share runs are
the sweep of $p_{\mathrm{acid}}$ given in Table~\ref{tab:x3-summary} above.
Inside each $R$-group the table pins every adaptive run between the two
fixed-share runs on either side of it. The two fixed-share borders are the
inconsistency levels reached under a specific $p_{\mathrm{acid}}$. Take the
adaptive and fixed-share runs at $R = 5$. With $c = 0.10$, inconsistency is
10.62\,\%. Its cleanest neighbour is the fixed-share run at $p_{\mathrm{acid}} =
  0.15$ with a 10.32\,\% inconsistency level, and its dirtiest neighbour is the
run at $p_{\mathrm{acid}} = 0.10$ with a 13.72\,\% inconsistency level. The
distance $d$ to the nearer of the two is defined as
\[
  d \;=\; \min\!\left(
  \frac{p_{95}^{\mathrm{adaptive}}}{p_{95}^{\mathrm{clean}}},\;
  \frac{p_{95}^{\mathrm{dirty}}}{p_{95}^{\mathrm{adaptive}}}
  \right)
\]

For this example the two candidates are $10.62 / 10.32 = 1.03$ towards the
cleaner side and $13.72 / 10.62 = 1.29$ towards the dirtier one, so $d = 1.03$.
The adaptive run sits 3\,\% away from a measured fixed-share run, which is the
value in the $R = 5$, $c = 0.10$ row of Table~\ref{tab:x3-matched}.

The fixed-share throughput in Table~\ref{tab:x3-matched} is therefore not read
straight out of Table~\ref{tab:x3-summary}. It is interpolated linearly between
the two neighbouring rows of that table at the $p_{95}$ of the adaptive run, so
both sides of the ratio are read at the same inconsistency level.

One candidate row is not considered, $(c = 0.20, R = 10)$. Its $p_{95}$ is
higher than the dirtiest fixed-share run of the $R = 10$ group, so it is dropped
rather than extrapolated. The row $(c = 0.20, R = 15)$ is degenerate
(Table~\ref{tab:x2-grid}) and is not considered either. The row $(c = 0.15, R =
  15)$ sits only 0.01 percentage points above the dirtiest fixed-share run of its
group, so it is kept and matched against that run alone.

The resulting throughput ratios are spread between $0.79$ and $1.12$, and they
depend on $R$. At $R = 1$ and $R = 5$ the two oracles are close, and a few
adaptive rows are faster. The largest gap is at $R = 5$ and $c = 0.02$. There
the adaptive oracle gives 0.1885\,tps and the interpolated fixed-share value is
0.1690\,tps, a ratio of 1.12. The gap is more than three seed standard
deviations, which are 0.0040\,tps for the adaptive run and 0.0033 and
0.0060\,tps for the two neighbours. At $R = 10$ and $R = 15$ the adaptive
oracle is slower in almost every row. At $R = 10$: ratios 1.04, 0.94, 0.90 and
0.86. At $R = 15$: ratios 0.85, 0.86, 0.79 and 0.81. The only faster row at
these $R$ is $R = 10$, $c = 0.02$, whose nearest neighbour is far away ($d =
  2.09$).

Restricting the comparison to the ten close rows, those where the nearest
neighbour lies within 12\,\%, shows the same dependence on $R$
(Table~\ref{tab:x3-close}). At $R = 1$ and $R = 5$ the ratios lie between 0.98
and 1.12. At $R = 10$ and $R = 15$ they are 0.94, 0.85 and 0.81. In all ten rows
the two oracles land on almost the same $\phi_{\mathrm{comp}}$ at matched
inconsistency. In different ways they control the same thing, the ACID share of
the completed work. The time share $\phi_{\mathrm{time}}$ differs more. In
seven of the ten rows the adaptive oracle has the higher value. This comparison
has to be read with care, because the two oracles measure $\phi_{\mathrm{time}}$
in different ways (Section~\ref{sec:exp-metrics}). For the adaptive oracle it
is the time in the global ACID mode. For the fixed-share oracle it is the time
after ACID draws.

\paragraph{One weakness of the adaptive oracle compared to fixed-share.} The
adaptive oracle switches to ACID mode at the moment when the dirty fraction
crosses the threshold $d_k \ge c$. This is when the system has reached the
critical level of inconsistency allowed. The dirtier the system gets, the longer
ACID transactions have to wait. Table~\ref{tab:x3-blocking} shows that at every
$R$ a larger share of the adaptive ACID transactions is blocked on a dirty or
BASE-claimed resource, and their mean wait is longer. This alone does not
explain the trend with $R$, because the blocked-share gap is just as large at $R
  = 5$, where the throughput of the two oracles is equal. The abort column follows
the trend better. At $R = 1$ and $R = 5$ the adaptive oracle aborts fewer or
about as many ACID attempts as fixed-share. At $R = 10$ and $R = 15$ it aborts
more in every row except $R = 10$, $c = 0.02$. At $R = 15$ and $c = 0.10$: 7.7\,\% against 4.6\,\%. This is
consistent with the complete switch of mode. While fixed-share starts ACID and
BASE in some mix at all times, the adaptive oracle starts all transactions in
ACID while the dirty fraction travels from the critical dirty threshold $c$
back down to the recovery threshold $r$. That likely leads to more ACID
transactions in flight at the same time, which compete for locks and abort more
often. The number of ACID transactions in flight is not measured directly.

\paragraph{Implications for a real software system.}
If we know that the workload will be static, we can adjust the proportion of how
many transactions should be started in the slow ACID mode, and how many in the
fast BASE mode. This would allow the throughput to be increased compared to pure
ACID while still controlling the inconsistency level of the system.

Fixed-share is as a result cheaper to run, since all configurations can be
started regardless of the internal system state, and more performant compared to
ACID. It gives up a stated limit on inconsistency. The comparison above is also
generous to fixed-share in two ways. First, its throughput is read from a curve
that was measured afterwards for each $R$. The $p_{\mathrm{acid}}$ that gives a
$p_{95}$ of about 10\,\% moves from about 0.17 at $R = 1$ to about 0.08 at $R =
  15$. An operator would have to tune the share again for each $R$ and each
workload, while the adaptive oracle uses the same $c = 0.10$ everywhere. Second,
fixed-share is much noisier across seeds. The median coefficient of variation
of its $p_{95}$ is 8.6\,\%, against about 0.7\,\% for the adaptive oracle. If
this tuning effort and spread are acceptable, the fixed-share split between ACID
and BASE could be a viable option.

\findingshead

\begin{bullets}
  \item[O8. A pair of $p_{\mathrm{acid}}$ and $R$ controls inconsistency.] Under
  constant load the pair $(p_{\mathrm{acid}}, R)$ reaches the inconsistency
  levels of the adaptive oracle within the sampled range
  (Table~\ref{tab:x3-summary}). The one exception is $R = 10$ and $c = 0.20$,
  which is dirtier than any fixed-share run at that $R$. So, with constant load
  we do not need to make a decision based on the internal system state. The
  chosen level of inconsistency can be reached by configuration of the ACID
  probability and the number of reconciliation processors, but the share has to
  be tuned for each $R$.

  \item[O9. Adaptive falls behind fixed-share at high $R$.] At matched
  inconsistency the two oracles are close at $R = 1$ and $R = 5$, with a few
  adaptive rows faster (up to 1.12). At $R = 10$ and $R = 15$ the adaptive
  oracle is slower, with ratios down to 0.79, as the comparison in
  Table~\ref{tab:x3-matched} shows. For RQ3 this means that, under a
  stationary load, choosing the mode from the internal state does not
  outperform a fixed split that was tuned for each configuration. Its advantage
  is that one setting of $c$ holds across all reconciler counts (O5).
\end{bullets}

\section{X4: Semantic overlap sweep}\label{sec:x4-overlap-sweep}

\emph{Semantic overlap} describes how tightly the models of a multi-model system
are tied to one another (Section~\ref{sec:prelim-overlap}). The \emph{semantic
  overlap} $\sigma$ is the share of the resources that carry a cross-model
consistency preservation rule. The simulator creates that set at the start of
each run and keeps it fixed. A transaction that works on a shared resource
spawns a bookkeeper transaction in another model. What happens next depends on
the mode of the transaction (Section~\ref{sec:approach-completion}). Under BASE
the root commits at once and the target resource stays dirty until a reconciler
clears it. Under ACID the bookkeeper joins the group of the root, and the root holds
its locks until the bookkeeper has finished. Semantic overlap therefore adds
work on both sides in a hybrid run. It fills the reconciler queue under BASE,
and it makes the ACID groups grow. A pure BASE root does not wait for its
bookkeepers, so pure BASE throughput does not depend on $\sigma$ at all. It
depends only on the $30 - R$ foreground processors. This is why the degenerate
cells of Table~\ref{tab:x4-overlap} show the same throughput at every $\sigma$,
equal to the BASE rows of X1.

This experiment gives more insight into RQ2, and especially into the part where
the critical dirty fraction threshold $c$ acts as the control for the level of
inconsistency. The \emph{semantic overlap} sets how dirty the system can become
at most. It is therefore important to see how the threshold $c$ behaves under
different values of the \emph{semantic overlap} $\sigma$.

\paragraph{Experiment configuration.} The sweep covers $\sigma \in \{0.00,
  0.05, 0.10, 0.20, 0.30, 0.50, 1.00\}$
against $R \in \{1, 5, 10, 15\}$ over five seeds, so 140 runs, under
\texttt{HYBRID\_ADAPTIVE} at the X1 baseline thresholds $c = 0.10$ and $r =
  0.05$. The $\sigma = 0.30$ block is the baseline shared with every other
experiment, and it reproduces the X1 adaptive rows. A cell in which the oracle
never switches is marked degenerate. The columns are defined in
Section~\ref{sec:exp-metrics}. The $p_{50}$ and $p_{95}$ columns come from the
dirty fraction $d$ sampled at every simulator step. $d_k^{\mathrm{switch}}$ is
the reading of the oracle. It is taken only at the moments when the
oracle switches to ACID mode, and it is averaged over all switches of the run.
Degenerate cells have no switch, so they have no value there.

\paragraph{The adaptive oracle engages only inside a range of
  $\sigma$.}\label{sec:x4-engagement} Thirteen of the 28 cells in
Table~\ref{tab:x4-overlap} are degenerate, and they are not random. Every cell
at $\sigma \le 0.10$ degenerates at every $R$, and so does $\sigma = 0.20$ at
$R = 15$. Those rows are pure BASE runs. The reason is that the semantic
overlap sets a hard ceiling on how much inconsistency is possible by design. The
oracle engages only where its reading $d_k$ reaches the threshold. At $\sigma =
  0.10$ the ceiling equals $c = 10\,\%$. One reconciler does not keep up. At $R
  = 1$ the dirty fraction is already pinned near the ceiling, with a $p_{95}$ of
9.62\,\%. It stays just under $c$ only because some repair targets collide. The
same happens at $\sigma = 0.05$, where the $p_{95}$ at $R = 1$ is 4.62\,\%
against a ceiling of 5\,\%. In the cells where the oracle does engage, more
semantic overlap raises the cost of a transaction. As a result throughput falls,
aborts rise, and the system spends more time in ACID. At $R = 1$:
$\phi_{\mathrm{time}}$ rises from 0.42 at $\sigma = 0.20$ to 0.77 at $\sigma =
  1.00$.

Figure~\ref{fig:x4-overlap-interval} plots the measured inconsistency against
\emph{semantic overlap} $\sigma$, with the configured critical dirty threshold
$c$ as the dashed line. In the shaded range from $\sigma = 0.20$ to $\sigma =
  0.30$ the $p_{95}(d)$ lands where it was configured. Across the seven engaged
cells there, as seed means, it is at most 0.87 percentage points away from $c$.
Per seed the deviation reaches 0.90. The shaded range also contains one
degenerate cell, $\sigma = 0.20$ at $R = 15$, with a $p_{95}$ of 8.23\,\%. The
0.87 comes from the baseline cell $\sigma = 0.30$, $R = 15$, which is shared with
X1 and X5. At $\sigma = 0.50$ the threshold starts to drift. $R = 10$ and $R =
  15$ are still within 0.87 (10.87\,\% and 9.67\,\%), while $R = 1$ and $R = 5$
are 1.46 and 1.47 percentage points above $c$. That is still close to what X2
accepts. At $\sigma = 1.00$ the threshold no longer holds, with a $p_{95}$ of up
to 22.51\,\%.

\paragraph{Why the $p_{95}(d)$ overshoots above the range.} The trigger works,
but the bound on $p_{95}$ does not. The oracle still engages where it was
configured to engage, and the $d_k^{\mathrm{switch}}$ column of
Table~\ref{tab:x4-overlap} shows it. In every engaged cell of the sweep the
oracle switches to ACID mode just above the configured $c = 10\,\%$. That column
hardly moves when $\sigma$ changes. At $R = 1$ it rises from 10.08\,\% to
10.73\,\%. The $p_{95}$ column in the same cells does move, and at $\sigma =
  1.00$ it reaches 22.51\,\%. The oracle therefore switches within about 0.7
percentage points of $c$.

What breaks the threshold is the work already in flight. A tag is fixed at
admission (Section~\ref{sec:approach-tagging-point}). A mode switch affects only
the transactions admitted after it, and not the 30 that are already running.
Those transactions keep writing, and every write to an overlapped resource
spawns a bookkeeper that inherits the BASE tag of its root, unless the target is
already dirty. The higher $\sigma$ is, the more of this background work each
write creates. Cascades happen at any $\sigma$, because each hop matches a rule
with probability $\sigma$. At $\sigma = 1.00$ every write matches, so the
writes of each root transaction cascade into bookkeepers that spawn further
bookkeepers. They dirty more resources than the root transaction touched
directly, and most likely they push the in-flight work past the threshold on
their own. No metric separates these marks from the reconciler backlog, which
is another possible source.

At full overlap that cascade looks endless. Every resource carries a rule, so
the resource a bookkeeper writes carries one too. The simulator bounds the
cascade with the bookkeeper depth, which is 5 in every run of this chapter
(Table~\ref{tab:exp-baseline}). A bookkeeper at that depth creates no children,
so each chain stops there. The limit applies at every $\sigma$, but only at high
$\sigma$ do chains often reach it.

\findingshead

\begin{bullets}
  \item[O10. $c$ holds only inside a range of $\sigma$.] The oracle needs enough overlap to fire at all. It also needs the
  overlap to stay small enough that one write does not dirty a large share of
  the resources in the background. Between those two limits, in the shaded range
  of Figure~\ref{fig:x4-overlap-interval}, the \emph{inconsistency level}
  $p_{95}(d)$ lands where it was configured. Below the range every cell is a
  pure BASE run. Above it a single write reaches so far that the transactions
  already admitted keep marking resources dirty in the background. The oracle
  still switches near $c$, but it cannot react to them, because their mode was
  fixed before the switch. So the trigger holds, while the bound on $p_{95}$
  does not.

  \item[O11. More reconcilers lower $p_{95}$ only partly.] The more the
  models overlap, the more background work every write creates. That background
  work comes from transactions that were tagged BASE before the switch. The
  transactions admitted after the switch pay the same overlap in the foreground
  instead, because every bookkeeper joins the group of its root. More
  reconciliation processors lower $p_{95}$, but they cannot bring it back to $c$
  at high $\sigma$. At $\sigma = 1.00$: 22.51\,\% at $R = 1$ and 14.53\,\% at
  $R = 15$. At $\sigma = 0.50$: 11.46\,\% at $R = 1$ and 9.67\,\% at $R = 15$.
\end{bullets}

\section{X5: Max number of resources per transaction
  sweep}\label{sec:x5-resources-sweep}

$L$ (\texttt{maxTransactionResources}) is the largest number of resources a
single transaction may touch. Each transaction draws its size uniformly from $1$
to $L$ and spreads those resources over up to four of the ten models. All other
settings stay the same as in Table~\ref{tab:exp-baseline}. $L$ only decides how
heavy one transaction is. Like X4, this experiment extends the answer to RQ2.
It tests whether the critical dirty threshold $c$ still holds when transactions
become lighter or heavier.

\paragraph{Experiment configuration.} The sweep covers $L \in \{5, 10, 25, 50, 100, 200\}$ against $R \in \{1, 5, 10,
  15\}$ over five seeds, 120 runs in total, under \texttt{HYBRID\_ADAPTIVE} with
$c = 0.10$, $r = 0.05$ and $\sigma = 0.30$. In Table~\ref{tab:x5-resources},
\emph{Lat.}\ is the mean transaction latency from creation to commit, and
\emph{Aborts} is the share of finished attempts that aborted
(Section~\ref{sec:exp-metrics}). Aborts are counted as events, so one
transaction can abort more than once.

\paragraph{A larger $L$ breaks the critical dirty threshold
  $c$.}\label{sec:x5-invariance} For $L \le 50$, the measured $p_{95}$ is at
most 0.87 percentage points away from the configured $c = 10\,\%$ at every
reconciler count. This is the same margin as in X4, because it comes from the
same baseline cell ($L = 50$, $\sigma = 0.30$, $R = 15$, with a $p_{95}$ of
9.13\,\%). Per seed the gap reaches 0.90. Above $L = 50$ the threshold breaks,
but not at every $R$ at once. At $R = 1$ and $R = 15$ it breaks from $L = 100$.
At $R = 10$ it breaks only at $L = 200$, since $L = 100$ still gives 9.49\,\%.
At $R = 5$ it stays close, with 11.18\,\% at $L = 100$ and 10.84\,\% at $L =
  200$. The measured $p_{95}(d)$ either overshoots or undershoots $c$, depending
on the number of reconciler processors $R$. Figure~\ref{fig:x5-size-band} shows
that $c$ holds as a threshold only while transactions stay small.

The main reason for this deviation from $c$ at large $L$ is the cost of a
transaction.
With more resources, the number of collisions with other transactions grows. In
addition, more background work is created. Table~\ref{tab:x5-resources} shows
that the latency of transactions grows with $L$. It takes longer for a
transaction to commit. As a result, throughput and admissions drop, and so does
the number of switches. At $R = 1$ it falls from 84 to 29, and at $R = 10$ from
634 to 40. Transactions most likely also wait longer in the queues, although
only end-of-run queue lengths are recorded. The direction of the inconsistency
level $p_{95}(d)$ is then decided by the number of reconciler processors $R$.
With a small $R$, it takes longer to clear dirty resources, and this causes the
overshoot. At $R = 1$ and $L = 200$: $p_{95}$ is 13.91\,\%. With $R \ge 10$,
transactions wait and throughput is low, so the reconciler processors clear
more dirty resources in the background. The $p_{95}$ then undershoots $c$. At
$R = 15$ and $L = 200$: $p_{95}$ is 7.37\,\%. The $p_{99}$ column shows that the
tail grows with $L$ at every $R$, also where $p_{95}$ undershoots.

  \item[O12. Size is paid for in the foreground.] Large transactions take
  much longer than their size alone explains, and they collide far more often. From $L = 5$ to $L = 200$ the mean size grows about 33 times. The mean

\section{The effective recovery threshold}\label{sec:effective-recovery}

This section reports no new experiment and belongs to RQ2. It takes a closer
look at the X2 runs with $c = 0.10$ and $r = 0.05$, averaged over the five
seeds. The oracle enters ACID when the dirty fraction reaches the critical
threshold $c$, and returns to BASE once it has fallen back to the recovery
threshold $r$. The previous sections reported only how the dirty fraction
relates to $c$. This section reports for the first time where the runs leave
ACID, and it shows that they undershoot the recovery threshold $r$. We call the
median level at which the oracle leaves ACID the \emph{effective recovery
threshold}.

Table~\ref{tab:effective-recovery} gives the readings of the oracle, $p_{50}(d_k)$
and $p_{95}(d_k)$, taken at the switch. The column ACID visit is the mean length
of one ACID visit. The column Drain is the time that reconciliation alone needs
to clear the dirty set from $c$ down to $r$, that is, 250 resources at $0.5R$
resources per second. The two check intervals are a proxy for how often the
oracle reads the inconsistency level. They are the time spent in each mode
divided by the number of committed root transactions tagged with that mode.
Readings themselves are not counted, and a transaction tagged in one mode can
commit in the other. Like all other values, these statistics include the
warm-up (Section~\ref{sec:exp-setup}).

The switch from BASE to ACID happens close to the configured threshold, at both
$p_{50}$ and $p_{95}$. The switch from ACID to BASE does not. The median lies
below the configured $r$ of 5\%. At $R = 1$: 1.08 points below. At $R = 15$:
2.39 points below. Figure~\ref{fig:recovery-exit} draws the exit switch against
the configured $r$, together with the shortfall of each point.

ACID visits are 2 to 3 times longer than Drain. At $R = 1$: 1075\,s against
500\,s. At $R = 15$: 100\,s against 33\,s. Part of this difference is expected.
A visit starts above $c$, because of the overshoot described in X2, and it ends
below $r$. So more than 250 resources are cleared in one visit.

\paragraph{Why the switch from ACID to BASE undershoots the recovery threshold
  $r$.}\label{sec:recovery-mechanism} The problem was already mentioned in the
previous experiments and in the approach description
(Section~\ref{sec:approach-sampling}). Here we explain it in more detail. The
oracle reads the inconsistency level only once per root transaction, at its
first admission attempt. Under \texttt{EQUILIBRIUM} a new root transaction is
created only when an in-flight one finishes. In ACID mode the 30 in-flight
transactions are slow, because they wait for locks and for dirty resources.
While all of them are stuck, no transaction finishes, no new one arrives, and
no reading is taken. Between two readings the value $d_k$ is therefore out of
date. The check interval columns in Table~\ref{tab:effective-recovery} show
this. At every $R$, the oracle reads less often in ACID mode than in BASE mode.
An example of this scenario follows. The inconsistency level is $d_k = 0.053$,
which is still above $r = 0.05$. For a long time no in-flight transaction
finishes, so no new transaction arrives and no reading is taken. Meanwhile the
reconciler processors clear the inconsistency in the background. When the next
transaction finally arrives, the level has already dropped to $d_{k+1} = 0.04$.
The oracle now switches back to BASE, because $d_{k+1} \le r$. So the next value
the oracle gets is already lower than the one it should react to.

The mean check interval shows the direction of the effect, but not its size.
Reconciliation drains about $0.5R$ resources per second. Multiplied by the mean
ACID check interval, this gives only about 0.5 percentage points between two
readings at every $R$. At $R = 1$: $0.5 \cdot 57.5 \approx 29$ resources. At
$R = 15$: $7.5 \cdot 3.3 \approx 25$ resources. The measured median undershoot
is 1.08 to 2.39 percentage points and grows with $R$. The size of the
undershoot therefore most likely comes from gaps between readings that are much
longer than the mean. The distribution of these gaps is not measured.

The miss has only one direction. By construction, the oracle can leave ACID only
at a reading at or below $r$, so switches from ACID to BASE are late and never
early. A run therefore ends up cleaner than its configuration implies. The
dirtiest exits ($p_{95}$) sit at 4.76 to 4.90\%, just under $r$ at every $R$.
This $p_{95}$ rests on few exits. At $R = 1$ a run has only about 23 exits, so
its $p_{95}$ is roughly the second-highest exit value.

\section{Summary of findings}\label{sec:exp-summary}

This section maps the findings of the chapter to the research questions. All
numbers are seed means under the stationary \texttt{EQUILIBRIUM} load.

\begin{bullets}
  \item[RQ1. Weak experimental evidence only.] RQ1 is answered by the design in
  Chapter~\ref{chapter:approach}. The experiments add only that none of the 140
  X1 runs stalls in 50\,000\,s (O1).

  \item[RQ2. Hybrid lies between ACID and BASE.] Where the adaptive oracle
  engages ($1 \le R \le 15$ in X1), it is faster than pure ACID and much slower
  than pure BASE (O2, O3). At $R = 1$: 1.7 times the ACID throughput. At $R =
    15$: 10 times the ACID throughput and 4.8 times lower than BASE. Its $p_{95}$
  stays within 0.62 percentage points of $c = 0.10$ (O4).

  \item[RQ2. The threshold $c$ is configurable.] Across $c = 0.02$ to $0.20$ and
  $R = 1$ to $15$, the measured $p_{95}$ is at most 1.5 percentage points away
  from $c$ in every engaged run (O5). The deviation is two-sided. The
  configurable range ends where BASE alone stays below $c$, which is set by
  $\sigma$ and $R$ (O6). A higher $c$ moves work from ACID to BASE (O7). On the
  way back, the oracle leaves ACID 1.08 to 2.39 percentage points below $r$
  (Section~\ref{sec:effective-recovery}).

  \item[RQ2. The threshold has limits.] $c$ holds for $\sigma$ between 0.20 and
  0.30 and for $L \le 50$. Above that range the oracle still switches near $c$,
  but $p_{95}$ drifts away from it (O10, O13). More reconcilers lower $p_{95}$
  only partly (O11), and $R$ decides whether the run overshoots or undershoots
  (O13).

  \item[RQ3. No advantage under stationary load.] A fixed ACID share, tuned for
  each $R$, reaches the same inconsistency levels (O8). At matched
  inconsistency the adaptive oracle is close to it at $R = 1$ and $R = 5$ and
  slower at $R = 10$ and $R = 15$, with ratios down to 0.79 (O9). Its advantage
  is that one setting of $c$ holds for every $R$, while the fixed-share oracle has to
  be tuned again and varies more across seeds. A varying load, where feedback
  should matter most, was not tested.
\end{bullets}



\begin{comment}
  \section{Threats to validity}\label{sec:exp-threats}

  \begin{itemize}
    \item \textbf{Stationary load only (\texttt{EQUILIBRIUM}).} Adaptive control
          would be expected to show its clearest advantage when the operating
          point moves, and constant load cannot test that. The claim is scoped
          accordingly in Section~\ref{sec:approach-why-hybrid}. The X3 claim
          about the pair $(p_{\mathrm{acid}}, R)$ (O8) is phrased in terms of
          transfer across \emph{configurations} rather than adaptation within a
          run. The stationarity of the load is stated at the head of
          Section~\ref{sec:x3-fixed-share-baseline} as well, because the
          throughput comparison there is run in the regime least favourable to
          feedback and should be read in that light.

    \item \textbf{Five seeds per configuration.} This is mitigated but not
          removed by how little the results move between seeds
          (Section~\ref{sec:exp-setup}). The fixed-share arm of X3 is the
          high-variance one. Its median seed CV on $p_{95}$ is 8.6\%, against
          about 0.7\% for the adaptive arm. So the O8 conclusion rests on the
          arm with the larger error bars. The throughput values behind the
          ratios of Table~\ref{tab:x3-matched} carry seed standard deviations
          of 0.002 to 0.023\,tps. This is small against the 0.79 to 1.12 range
          of the ratios themselves. It is still computed from five runs and
          should be read as an indication rather than an interval. The
          smoothing sweep of the appendix is the exception at three seeds. Its
          conclusion is independently confirmed at five by the X1 and X2
          re-runs reported there.

    \item \textbf{\texttt{reconciler\_busy\_fraction} is misnamed.} It is not a
          utilisation but the fraction of samples in which \emph{every}
          reconciler was busy at the same instant. It is taken once per
          simulated second against a service time of two seconds. The phase
          relationship between the two makes it unreliable. It reads 0.5 at $R
            = 1$ and 0.0 at $R \ge 10$ under pure BASE, while the same runs
          sustain about $0.5R$ completed reconciliations per second, a pool
          that is in fact fully saturated. Saturation is read in this chapter
          from the completion rate instead
          (Section~\ref{sec:effective-recovery}). No result uses this column,
          and it should not be read from the exported CSVs.

    \item \textbf{$R = 0$ is a different mechanism, not zero capacity.} At $R =
            0$ the CPR work is queued on the main processors, so the run has
          no dedicated reconciliation pool. It has about 963\,k mark events
          against 26\,k at $R = 1$. The $R = 0$ rows are a reference line and
          are not points on the same capacity axis as $R \ge 1$.

    \item \textbf{Simulated rather than real execution, and a single workload
            shape.} The absolute numbers are properties of the simulator. The
          comparisons between configurations are the transferable part. The
          service times are fixed (IO 200\,ms and CPU 100\,ms per resource),
          the bookkeeper depth is 5, the referential action is
          \texttt{ON\_CASCADE}, and transaction sizes are uniform in $1$ to
          $L$. That is one workload shape.

    \item \textbf{The recovery threshold is never swept.} Every run uses $r =
            0.5c$. How the results depend on the width of the hysteresis band
          is therefore not tested.

    \item \textbf{Warm-up.} The warm-up window applies only to two steady-state
          columns. All reported values include the first 5000\,s. The effect
          on the percentiles is at most about 0.1 percentage points.

    \item \textbf{Few switch events per run.} At $R = 1$ and $c = 0.10$ a run
          has only about 23 exits from ACID. Percentiles of the switch levels
          in Table~\ref{tab:effective-recovery} are therefore noisy.

    \item \textbf{The matched comparison of X3 reads between measured points.}
          The fixed-share arm is sampled at five values of
          $p_{\mathrm{acid}}$, and Table~\ref{tab:x3-matched} reads its
          throughput at intermediate values of $p_{95}$ rather than at
          measured ones. Ten of the 18 comparisons land within 12\% of a
          measured fixed-share run and one needs no estimate at all. The other
          rows lean on the straight line between two runs that can be far
          apart. The reconciler-count trend of Section~\ref{sec:x3-frontier}
          survives the restriction to the ten close rows of
          Table~\ref{tab:x3-close}, but no single distant row is read on its
          own. The interval $p_{\mathrm{acid}} \in (0, 0.05)$ is unsampled and
          contains the steepest part of the trade-off. A finer grid there,
          together with settings between $p_{\mathrm{acid}} = 0.10$ and
          $p_{\mathrm{acid}} = 0.25$ to bracket the tight-threshold adaptive
          cells, would turn most of these readings into measurements and close
          the one cell where the two arms do not overlap at all.

    \item \textbf{The workload sweeps vary one axis at a time.} X4 and X5 each
          find a band over which the threshold holds, one in semantic overlap
          and one in resources per transaction. Each holds the other axis at
          its baseline, so the corner where both are extreme is unsampled. The
          overshoot at small $R$ has the same likely source in both sweeps,
          work already admitted that no switch can recall. The undershoot of
          X5 at $R \ge 10$ has a different source, waiting and low throughput.
          The corner is therefore the one most likely to behave differently.

    \item \textbf{The smoothing sweep cannot be re-run against current code.}
          The \texttt{alpha\_sweep} results behind the appendix are archived
          under \texttt{experiments-old-ewma-0.2/} and the tables can be
          regenerated from them. The parameter they sweep no longer exists
          in the simulator, so the runs themselves cannot be reproduced without
          reverting the removal. The X1 and X2 re-runs that confirm the removal
          are reproducible against current code. The smoothing grid is
          reproducible only from the archive.
  \end{itemize}
\end{comment}
