\chapter{Preliminaries}\label{chapter:preliminaries}

This chapter describes the background that the later chapters use. Each
section builds on the previous one. Section~\ref{sec:prelim-transactions}
defines a transaction, the ACID guarantees, the locking rule that provides
them, and BASE, which gives up part of these guarantees.
Section~\ref{sec:prelim-simulator} describes the basics of the simulator that
this thesis extends. Section~\ref{sec:prelim-multimodel} explains the
multi-model system it simulates, where a write in one model requires updates in
other models. It shows how ACID and BASE carry out these updates and how the
resulting inconsistency is measured. Section~\ref{sec:prelim-hysteresis} covers
the hysteresis band, which the adaptive oracle uses.
Section~\ref{sec:prelim-notation} lists the symbols used in the thesis.


\section{Transactions, ACID and BASE}\label{sec:prelim-transactions}

\paragraph{Transactions.}\label{sec:prelim-serialisability}
A transaction is a group of read and write steps on resources that takes effect
as one unit. When several transactions run at the same time, the result must be the same as if
they had run one after another. This property is called serialisability.

\paragraph{ACID.}\label{sec:prelim-acid}
ACID names four guarantees that a transactional system gives. Atomicity means
that all steps of a transaction take effect or none of them do. Consistency
means that a committed transaction leaves the data in a valid state. Isolation
means that concurrent transactions do not see each other's unfinished work.
Durability means that a committed result is not lost afterwards. Isolation is
the most expensive of the four, and it is provided by locking.


\paragraph{Locking.}\label{sec:prelim-2pl}
A transaction declares the resources it will work with and has to acquire a lock
on each of them before it can start. No other transaction can lock these
resources until the locks are released after the last step. Acquiring the whole
set in advance is called \emph{preclaiming}, and the scheme is known as
conservative two-phase locking. It rules out deadlock, because a transaction
never waits while it holds a lock~\cite{ries1979locking}.

\paragraph{BASE.}\label{sec:prelim-base}
BASE gives up immediate consistency to gain availability and
throughput~\cite{pritchett2008base,vogels2009eventually}. A transaction commits
as soon as its own work is done. It does not wait for the work it causes in the
rest of the system. That work runs later in the background, and the system
becomes consistent again over time.

\section{The base simulator}\label{sec:prelim-simulator}

This thesis extends the simulator of Zacouris and
Acosta~\cite{zacouris2025m2ts,zacouris2026mxs}. This section covers only its
basics.

\paragraph{The execution engine.}\label{sec:prelim-engine}
Time advances in fixed steps of one simulated second. A new transaction waits in
a pending queue until it is admitted. It then passes through a lock phase, an IO
phase and a CPU phase on pools of IO and CPU processors, and finally it commits
or aborts. ACID transactions use conservative two-phase locking
(Section~\ref{sec:prelim-2pl}). BASE transactions skip the lock phase, and
conflicting writes are resolved by a last-write-wins rule. The clock is virtual,
so the results do not depend on the speed of the machine.

\paragraph{Simulator parameters.}\label{sec:prelim-parameters}
A run is configured by the number of resources, models and locks, the number of
IO and CPU processors, and the execution mode, ACID or BASE, which holds for the
whole run. It is also configured by the maximum number of resources $L$ and of
models that one transaction may touch. The multi-model parameters are introduced
in Section~\ref{sec:prelim-multimodel}. Table~\ref{tab:exp-baseline} gives the
values used in this thesis.


\paragraph{Workload.}\label{sec:prelim-workload-profiles}
The simulator creates its own transactions. Each transaction draws at random how
many resources and models it touches, and which ones. A seed makes this sequence
reproducible. This thesis uses the \texttt{EQUILIBRIUM} profile, which keeps the
number of in-flight transactions constant. Whenever one transaction finishes, a
new one is created. A second profile,
\texttt{TERMINAL}, lets the load rise and fall, but it was still under
development and is not used (Section~\ref{sec:approach-stationary-load}).

\section{Multi-model systems and consistency preservation}\label{sec:prelim-multimodel}

\paragraph{Models and semantic overlap.}\label{sec:prelim-overlap}
A model is a set of resources that describes one view of a
product~\cite{klare2021vitruvius}. A multi-model system is a finite set of
resources $\mathcal{X}$ with $|\mathcal{X}| = N$, divided between the models
$M_1, \dots, M_m$. Two models have \emph{semantic overlap} when they contain
resources that represent the same fact. The overlap degree $\sigma$ is the
fraction of resources that overlap between models~\cite{zacouris2026mxs}.

\paragraph{Consistency preservation rules.}\label{sec:prelim-cprs}
A consistency preservation rule (CPR) states that a write to one resource
requires updates to the resources that overlap with it. In the notation of this
thesis, a rule maps a write on a resource $x$ to the set
$\mathrm{cpr}(x) \subseteq \mathcal{X}$ of resources that must be updated as a
consequence~\cite{zacouris2026mxs}. An update made by a rule can trigger further
rules, up to a maximum depth. One write can therefore reach resources in several
models. Figures~\ref{fig:cpr-expansion-acid} and~\ref{fig:cpr-expansion-base}
show such a chain of rules across five models.

\paragraph{Bookkeepers.}\label{sec:prelim-expansion}\label{sec:prelim-bookkeeper}
A transaction that arrives from the workload is called a \emph{root}
transaction. When it writes a resource $x$, the resources in $\mathrm{cpr}(x)$
must also be updated. These updates are made by separate transactions, called
\emph{bookkeepers}. A bookkeeper may itself trigger further rules, and then it
creates bookkeepers of its own. Every bookkeeper runs in the same execution mode
as the transaction that created it. \emph{Rule expansion} is the step that
creates the bookkeepers of a transaction. It runs after that transaction has
finished its work, because the targets of a rule depend on what was actually
written (Section~\ref{sec:approach-completion}). The following paragraphs
describe how ACID and BASE execute the bookkeepers.

\paragraph{Transaction groups.}\label{sec:prelim-group}
A root transaction and all the bookkeepers that follow from it form a
\emph{transaction group}~\cite{zacouris2026mxs}. Under ACID the group commits as
one unit, and if one member is blocked or aborted, so is the whole group. The
bookkeepers are not known when the root is admitted, so the root preclaims only
its own locks. The bookkeepers add their locks later, and all locks are released
when the group commits (Figure~\ref{fig:cpr-expansion-acid}). A group can
therefore wait while it holds locks, and two groups can wait on each other.

\paragraph{Cautious waiting.}\label{sec:prelim-deadlock}
The base simulator prevents such a deadlock with cautious
waiting~\cite{hsu1992cautious,zacouris2026mxs}. A transaction may queue for a
lock only if the group that holds it is not blocked itself. Otherwise its group
is aborted, releases all of its locks and is retried later. A pure ACID run
therefore cannot deadlock, but it loses aborted work
(Section~\ref{sec:approach-group-locking}).

\paragraph{Dirty resources and reconciliation.}\label{sec:prelim-reconciliation}
Under BASE a root transaction commits without waiting for its bookkeepers. Until
a bookkeeper has committed, the resource it updates holds an old value and is
called \emph{dirty}. \emph{Reconciliation} runs the pending bookkeepers in the
background on $R$ reconciler processors, taken from the IO and CPU processors
(Figure~\ref{fig:cpr-expansion-base}). Under ACID $R$ is ignored.

\paragraph{Inconsistency.}\label{sec:prelim-inconsistency}
The dirty set $D_k \subseteq \mathcal{X}$ holds the dirty resources at reading
$k$, and $d_k = |D_k| / N$ is the \emph{dirty fraction}. A run is summarised by
its 95th percentile $p_{95}(d)$, which is the value bounded in
Equation~\ref{eq:problem}. Under pure ACID $d_k$ is always zero.


\section{Hysteresis band}\label{sec:prelim-hysteresis}

A policy that switches between two states with a single threshold switches at
every crossing when the measured value moves around it. It pays the cost of each
switch without gaining from it. A \emph{hysteresis band} uses two thresholds
instead, one for entering a state and a lower one for leaving it. The next
switch happens only after the value has crossed the whole band.
Section~\ref{sec:approach-adaptive-oracle} applies this to the adaptive oracle.
