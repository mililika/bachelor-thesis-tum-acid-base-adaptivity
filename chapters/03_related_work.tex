\chapter{Related Work}\label{chapter:related-work}

This chapter describes how the thesis integrates into existing literature.
Section~\ref{sec:rw-simulators} covers transaction simulators and the base
simulator that this thesis extends. Section~\ref{sec:rw-mode-selection} explains
systems that already choose an execution mode per transaction at runtime.
Section~\ref{sec:rw-acid-base} describes work that combines strong and weak
consistency in one system. Section~\ref{sec:rw-multimodel} focuses on the
multi-model framework. Section~\ref{sec:rw-gap} summarizes what was built upon
and what was added with this thesis.

\section{Simulation of transactional systems}\label{sec:rw-simulators}

It is hard to study concurrency control in real-world systems. As a result of
that, we will work with a simulator that allows us to compare different policies under
the same synthetic workload. This section first covers two single-model studies
and then the two papers of the base simulator.

\paragraph{Single-model simulators.} Ries and Stonebraker~\cite{ries1979locking}
simulate the load of a database to study how the size of locks affects
performance. Dandamudi and Au~\cite{dandamudi1991locking} repeat this study for
a database that runs on several processors. Both simulators keep a fixed number
of transactions in-flight. Each transaction moves through a specific pipeline.
It starts with a pending queue, an IO queue, and a CPU queue, and it waits in a
blocked queue when a lock it needs is taken.

The base simulator, and therefore this thesis, takes this structure of queues
and the fixed number of transactions. The base simulator~\cite{zacouris2026mxs} is also validated
against the results of Dandamudi and Au~\cite{dandamudi1991locking}. Both studies
consider a single model with ACID execution only.

\paragraph{The multi-model simulator M2TS.} Zacouris and
Acosta~\cite{zacouris2025m2ts} carry this method over to multi-model systems. In
their simulator, an update to one model can trigger updates in others. The
simulator supports ACID only.

Its main result is that throughput drops towards zero as the number of models
increases, and that lock acquisition is the bottleneck.

\paragraph{ACID and BASE in the same simulator.} The follow-up
study~\cite{zacouris2026mxs} adds the BASE semantic and is the
direct base of this thesis. Under BASE, a transaction takes no locks, and the
triggered updates run later in the background on dedicated reconciliation
processors. The study also measures inconsistency as the share of resources that
wait for such an update.

Its results are the starting point of this thesis. Under ACID, throughput falls
sharply as the overlap of the models increases. Under BASE, throughput is almost
unaffected, but the system carries a temporary inconsistency. The amount of
inconsistency is controlled by the number of reconciliation processors.

In the base simulator, ACID and BASE are two separate configurations, and one run
uses only one of them. This thesis lets both modes run in the same run, chooses
the mode per transaction at admission, and makes the inconsistency a
configurable parameter.

\section{Deciding an execution mode at runtime}\label{sec:rw-mode-selection}

The work in this section is the closest to the design of this thesis. These
systems tag each transaction with one of several execution modes at runtime. The
most important of them is Hybrid Transactional Replication, because several
parts of the approach in Chapter~\ref{chapter:approach} follow its approach.

\paragraph{Hybrid Transactional Replication.} Kobus et al.~\cite{kobus2018htr}
study one service whose data is fully replicated on several machines. Each
transaction runs in one of two modes. In \emph{state machine} mode, the request
is sent to all replicas, and every replica executes it in the same order. In
\emph{deferred update} mode, only the replica that received the request executes
it, and at commit, its updates are sent to all other replicas, which check them for
conflicts and apply them. A component called the \emph{oracle} chooses the mode
for each transaction. Their learned oracle, HybML, reaches up to 50\% higher
throughput than using only one of the two modes.

This thesis takes three ideas from HTR. The mode is chosen per transaction,
both modes are active in the same system, and the choice is made by an oracle
behind a small interface (Section~\ref{sec:approach-hybrid}).

The main difference lies in the configuration. HTR replicates one data set, and
a replica never creates background work. This thesis focuses on a multi-model
system, where independent models share some of the resources, receive their own
requests, and trigger updates in each other.

The second difference is what the modes guarantee. Both HTR modes are strongly
consistent, while BASE in this thesis leaves dirty resources for background
reconciliation. This creates the shared state that the arbiter has to manage
(Section~\ref{sec:approach-arbiter}).

Finally, HybML maximizes throughput, while the adaptive oracle in this thesis
focuses on a configurable dirty resource fraction threshold.

\paragraph{PolyCert and MorphR.} PolyCert~\cite{couceiro2011polycert} makes the
same kind of choice in replicated in-memory data grids, where a learned oracle
picks one of three certification protocols for each transaction.
MorphR~\cite{couceiro2013morphr} switches the replication protocol of the whole
system instead of a single transaction. As in HTR, all their modes keep the data
strongly consistent, and the oracles optimize only throughput and latency.

\section{Combining strong and weak consistency}\label{sec:rw-acid-base}

The work in this section lets strong and weak consistency exist in the same
system, as ACID and BASE do in this thesis.
Section~\ref{sec:rw-static} covers Salt and RedBlue consistency. They run strong
and weak work side by side, but the consistency type has to be set by a
developer before the system runs. Section~\ref{sec:rw-adaptive} covers
Consistency Rationing, OptCon, epsilon-serializability, and TACT. They change the
consistency level at runtime or put an inconsistency under threshold, but none
of them decides whether a whole transaction with its triggered updates runs as
ACID or BASE.

\subsection{Static classification of transactions}\label{sec:rw-static}

\paragraph{Salt.} Xie et al.~\cite{xie2014salt} make ACID and BASE transactions
run in the same distributed database. A developer rewrites only the few
transactions that limit performance as BASE transactions, and all other
transactions stay ACID. The rule that keeps this combination safe is \emph{Salt
  Isolation}. To an ACID transaction, a BASE transaction looks like just another
ACID transaction, so ACID never sees unfinished BASE work. BASE transactions,
however, may see each other's work in progress, so their locks collide less
often.

\paragraph{RedBlue consistency.} Li et al.~\cite{li2012redblue} make a similar
split for geo-replicated systems, but per operation. A \emph{blue} operation
runs first at the node that received it, without waiting for others, and is
sent to the other nodes later. Different nodes may therefore apply blue
operations in different orders. A \emph{red} operation is placed in one order
that all nodes follow, so it needs coordination. An operation may be blue only
if the order does not change the final state, and if it does not corrupt the
system state.

\vspace{1.8ex plus .4ex minus .2ex}
\noindent Both papers show that strong and weak consistency can safely run in one system.
Salt is also the closest precedent for the arbiter of this thesis, because its
ACID transactions wait for BASE work to finish, while BASE transactions may see
each other's unfinished work. The claim table of Section~\ref{sec:approach-claim-table}
follows the same idea. What these papers do not do is decide the mode at
runtime. In both systems, the split is made by hand and is fixed in the source
code before the system runs. They also do not measure or bound how much
inconsistency exists.

\subsection{Adaptive and bounded
  consistency}\label{sec:rw-adaptive}\label{sec:rw-bounded}

\paragraph{Consistency Rationing.} Kraska et al.~\cite{kraska2009rationing}
attach consistency guarantees to data instead of to transactions. Some data is
always serializable, some only has weak consistency, and the rest switches
between the two at runtime, for each record. In a web shop, for example, account
balances are always serializable, user preferences are weakly consistent, and
the stock of a product becomes serializable only when few items are left. A
policy makes the switch, for example, when the estimated probability of a
conflict becomes too high. The goal is to lower the total cost of transactions
and of inconsistencies.


\paragraph{OptCon.} Sidhanta et al.~\cite{sidhanta2016optcon} choose a
consistency level for every read and write in a quorum-based store such as
Cassandra. The user states a latency limit and a staleness limit, and a trained
model predicts which consistency level meets both.

\paragraph{Epsilon-serializability and TACT.} Pu and Leff~\cite{pu1991esr} and
Wu et al.~\cite{wu1992divergence} let a read-only transaction see a limited
amount of inconsistency, while update transactions stay serializable. Yu and
Vahdat~\cite{yu2000conit} bound how far the copies of replicated data may drift
apart, with limits that the application sets for each unit of data. Both approaches treat
inconsistency as a number with a limit. The critical dirty threshold of this
thesis is a limit of this kind.

\vspace{1.8ex plus .4ex minus .2ex}
\noindent All of this work changes or bounds consistency based on what the system
observes, which is the idea behind the adaptive oracle and critical dirty
threshold. The difference is what is decided and where the limit is set.
These papers work per record, per operation, or per unit of data, but none of them
decides whether a whole transaction and the repairs it triggers run as ACID or
BASE. Their limits are also set for a single transaction, as in
epsilon-serializability, or for single units of data, and none keeps one
inconsistency level for the whole system, like the dirty fraction in
this thesis.

\section{Multi-model consistency preservation}\label{sec:rw-multimodel}

\paragraph{Vitruvius.} Klare et al.~\cite{klare2021vitruvius} provide the
setting of this thesis. Vitruvius keeps the overlapping models of a system
separate and connects them into a \emph{virtual single underlying model}. A
change in one model is propagated to the other models by consistency
preservation rules. This is the mechanism that creates the workload studied
here, and the base simulator is calibrated with measurements from two systems
built with Vitruvius~\cite{zacouris2026mxs}.

Vitruvius applies changes sequentially. After each change, the rules run until
all models are consistent again, and only then is the next change started. This
gives a consistent state after every change without any concurrency control.

\section{Discussion and delimitation}\label{sec:rw-gap}

Except for the two papers of the base simulator, all work focuses on data under a single schema. There, inconsistency means, for example,
replicas that differ, unfinished work that other transactions may see, or a
query result that is off by a limited amount. The inconsistency that updates create
between overlapping models is not addressed. Vitruvius addresses these models,
but it has no transactions and no deferred repairs. This thesis works in the
space between the two. It chooses ACID or BASE per transaction at runtime in a
multi-model system, and keeps the resulting inconsistency close to a configured inconsistency
threshold.
