\chapter{Approach}\label{chapter:approach}

This chapter describes how the received simulator was extended so that it
supports the hybrid mode. Section~\ref{sec:approach-delta} lists which parts are inherited
and which are new. Section~\ref{sec:approach-why-hybrid} explains why a hybrid
mode is needed. Section~\ref{sec:approach-pipeline} shows how the received
simulator runs only one mode per run.
Section~\ref{sec:approach-hybrid} adds the hybrid mode on top of it.
Section~\ref{sec:approach-arbiter} covers the shared-resource arbiter, which
keeps ACID and BASE from breaking each other's work.
Section~\ref{sec:approach-oracles} describes the two oracles that choose the mode
of each transaction. Section~\ref{sec:approach-deadlock} defines what \emph{safe}
means in this work and argues that the hybrid mode meets this definition.

\section{Introduction of hybrid mode}\label{sec:approach-why-hybrid}

The purpose of the hybrid mode is to combine the ACID and BASE semantics in
the same run. The share of each mode then becomes a way to control metrics
such as throughput and inconsistency. ACID is the slow but consistent
approach. Its dirty fraction $d_k$ is always zero, but its throughput drops
sharply as the number of resources and models grows~\cite{zacouris2026mxs}.
BASE hands the work that has to be propagated to other models over to the
reconciler pool, which clears the updates eventually. However, BASE gives no
control over the inconsistency of the system, and the dirty set can grow
faster than the reconcilers are able to clear it.

Table~\ref{tab:approach-added} lists the components of the hybrid mode that
were introduced in this thesis, with a reference to the section where each of
them is described in more detail.

\section{Received simulator allows only one mode per run}\label{sec:approach-pipeline}

The simulator can run ACID or BASE, but never both. A run binds its
configured concurrency model through the \emph{runtime assembler}, and there
is one assembler per mode. It builds every mode-dependent collaborator at the
start of the simulation, so all transactions run in the one mode that was
assembled at the beginning. Figure~\ref{fig:pipeline} shows how the
mode-specific components are wired. While explaining how the two modes are
started, this section also follows the path that one ACID or one BASE
transaction takes, because the hybrid mode reuses that path.

At the start of the simulation, the runtime assembler (Step 1 in
Figure~\ref{fig:pipeline}) creates either ACID or BASE wiring. Only
one path exists in the simulator at a time. For example, when the simulator
is configured in ACID mode, none of the BASE components are built, and vice
versa. Only the parts that do not depend on the mode, such as the execution
engine and the first part of admission, are the same in both wirings.

Admission (Step 2) has two parts, and the rest of this chapter keeps them apart. The admission controller takes the
next transaction from the pending queue. The second part is the
\emph{mode admission step}, which admits the transaction only while the number of
transactions in flight is below the capacity limit, and it differs between the modes.


BASE has no locking step and admits the transaction straight into execution.
ACID first acquires the whole lock set of a parent transaction at once, or waits
while holding none of it. A transaction counts as \emph{admitted} only once it
has passed the mode admission step. A new transaction that arrives from the
workload is not admitted yet. It only joins the pending queue. The concurrency
strategy and the transaction executor (Steps 3 and 4) then drive the phases
\texttt{LOCK}, \texttt{IO}, \texttt{CPU}, and \texttt{COMPLETE}, and BASE skips
\texttt{LOCK}.\label{sec:approach-execution}

In BASE mode, the processor pool is split into two sets. The first is the
foreground processors, which handle the initial parent transactions. The second
is the reconciler pool, which propagates the changes to the other models. The
simulator allows both the number of foreground IO and CPU processors and the
number of reconciler processors to be configured. In BASE, the number of reconciler
processors is subtracted from the pool of foreground processors. In ACID, the
reconciler processor count is ignored. The hybrid mode described below keeps
the BASE rule, so in a HYBRID run, the ACID transactions also use the smaller
foreground pool. After a parent transaction is processed, rule expansion (Step
5) decides what happens next.\label{sec:approach-completion} ACID parks the
parent in the waiting room (\texttt{WAITING ROOM} in
Figure~\ref{fig:hybrid-queueing-acid}), where it waits for its group, and spawns its bookkeepers, which have to go
through the same process of acquiring locks. BASE commits the parent immediately
and then starts its bookkeepers independently, without waiting for them.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\textwidth]{fig-received-pipeline.pdf}
  \captionsetup{format=plain,justification=centering}
  \caption{The received pipeline.}
  \label{fig:pipeline}
\end{figure}

One property of the ACID mode is important. The unit of locking is the group and
not the transaction, because the root preclaims its own set at admission while
its bookkeepers extend that set afterwards.\label{sec:approach-group-locking}
A group can therefore be blocked while it already holds locks, and two groups
can wait on each other. The received simulator prevents this with cautious
waiting (Section~\ref{sec:prelim-deadlock}), which uses two abort rules. First,
a transaction that asks for a lock held by a blocked group is aborted instead of
being queued. Second, when a group becomes blocked, the transactions already queued on
its locks are aborted.

The components of Steps 2 to 5 each exist in an ACID form and a BASE form, and
the assembler of Step 1 picks one form at the start. A run, therefore, inherits
one execution mode and keeps it to the end.\label{sec:approach-seams}

The idea of the hybrid mode is to keep both modes and to wrap each of these
components in a dispatcher that holds one collaborator of each kind.

\section{Implementing the hybrid mode}\label{sec:approach-hybrid}

A third execution mode, \texttt{HYBRID}, is added next to ACID and BASE. It
is not a third set of semantics, but a configuration in which both received
sets are live at the same time. What the hybrid mode adds is the choice of
which mode a transaction runs in.

\paragraph{Dispatchers wrap both paths.}\label{sec:approach-dispatchers} A third
runtime assembler builds both mode-specific sets in full and wraps each pair.
Every component of Section~\ref{sec:approach-pipeline} is then filled by a
dispatcher that holds one ACID collaborator and one BASE collaborator, and
forwards each call to the one that the transaction names. Both ACID and BASE
paths are left unchanged. The two admission controllers share the scheduler, the
processors, the I/O model, the queue manager, and the capacity limit, and the two
bookkeeper coordinators share the dirty set and the lock table. The dispatchers
and the arbitration checks are built by the hybrid assembler only, so a pure
ACID or pure BASE run still executes as in the received simulator.

\paragraph{Introduction of tag and mode
  oracle.}\label{sec:approach-oracle-interface}\label{sec:approach-tag}\label{sec:approach-tagging-point}
Since both modes are wired into the simulator at the same time, the decision
which path to take has to move out of the assembler. Our approach introduces a
tag for each transaction. Only two tags exist: \emph{\{ACID, BASE\}}. Each transaction
receives its tag once, and the tag is propagated to the bookkeepers of that
transaction. Choosing an execution mode per transaction at runtime is not new in
itself. Hybrid Transactional Replication~\cite{kobus2018htr} and
PolyCert~\cite{couceiro2011polycert} already do it, but there, all modes give the
same consistency, so the choice is never about controlling the inconsistency level
(Section~\ref{sec:rw-mode-selection}).

The tag is chosen by a component called the \emph{mode oracle}. It is
implemented as a Java interface with a single method, \texttt{assignMode()}.
This thesis introduces two mode oracles, which are described in
Section~\ref{sec:approach-oracles}. The oracle is called as soon as the
admission controller takes an untagged parent transaction from the pending
queue. The mode oracle returns the mode in which the
transaction should run. The dispatcher then hands the transaction to the
admission controller of that mode, which runs the
\emph{mode admission step}, either ACID or BASE. A tagged transaction that finds
no free capacity keeps its tag and waits for capacity like any other.

Tags are immutable. They cannot be withdrawn or changed. Once a transaction has
received its tag, it stays in that mode for its whole life, and so do all of its
bookkeepers. The same holds when a transaction is aborted. It loses all its
progress, but not its tag.

\paragraph{Sharing one resource pool and the limits of the naive
  design.}\label{sec:approach-resource-layer}\label{sec:approach-mixing-hazard}
One set of resources is created at the beginning and is never divided again.
At the baseline, that is $5000$ resources, divided equally between the $10$
models. An ACID-tagged transaction may lock any of the $5000$
resources, and a BASE-tagged transaction may dirty any of the same $5000$.

Simply wrapping both modes is a naive design here. It separates the path a
transaction takes, but the resources that the transaction needs are still shared. The
problem is that the lock table used by ACID and the dirty set used by BASE
do not communicate. As Figure~\ref{fig:hybrid-resources} shows, both modes
ignore the progress of the other when they work on the same resource. ACID
locks are visible only to other ACID transactions, and BASE dirty marks only
to other BASE transactions. This would break the isolation that ACID
promises, because a locked resource could be overwritten while it is locked.

\begin{figure}[H]
  \centering
  \includegraphics[width=\textwidth]{fig-hybrid-resources.pdf}
  \captionsetup{format=plain,justification=centering}
  \caption{Resource management in the hybrid mode.}
  \label{fig:hybrid-resources}
\end{figure}

A resource that is ACID-locked and BASE-dirty at the same time is in an
undefined state, because each half relies on an assumption that the other
half breaks. Sharing the pool is therefore only half of what a hybrid run
needs. The other half is a shared-resource arbiter. It connects the
bookkeeping of the two pure modes and defines what a mode does when a
resource it needs is in use by the other mode. The next section addresses this problem.

\section{The shared-resource arbiter}\label{sec:approach-arbiter}

Section~\ref{sec:approach-mixing-hazard} left the hybrid mode with one open
problem. Both halves write to the same resources and ignore the work of the
other half. The lock table is asked only whether a lock is free. The dirty
set is asked only whether a repair is in progress. Nothing in that
scenario stops a resource from being locked and dirty at the same time.

This section describes the shared-resource arbiter, the mechanism
introduced to solve this isolation problem between the ACID and BASE
bookkeeping.

\paragraph{Arbiter implementation.}\label{sec:approach-arbiter-lookup} The
arbiter is not a single class that holds references to all resources or
locks. It reuses two existing records, the lock table and the dirty set,
and adds a third one, the claim table.
Figure~\ref{fig:arbiter-layer} shows how the three records are connected.
Every lookup starts from the same place, the name of a resource in the
shared pool (column 1). An ACID transaction, a BASE parent, and a BASE repair
all start from that name when they want to use resource $\mathit{res}_k$.
The name is then mapped to a key (column 2). The lock table and the claim
table both use the lock id, which the granularity mapping computes from the
resource. A run may be configured with fewer locks than resources, so one
lock id can cover several resources. The dirty set uses the dirty key, the
pair of the owning model and the resource, so it always has one entry per
resource. Under its key, each record keeps one entry (column 3). The lock
table lists the ACID transactions holding the lock, the claim table lists
the BASE parents writing under it, and the dirty set holds the
repair that is still outstanding on the resource. Because both keys are
computed from the same resource name, any path can look up any record
without extra bookkeeping.

\begin{figure}[H]
  \centering
  \includegraphics[width=\textwidth]{fig-arbiter-layer.pdf}
  \captionsetup{format=plain,justification=centering}
  \caption{The shared lookup the arbiter is built on.}
  \label{fig:arbiter-layer}
\end{figure}

The colors in Figure~\ref{fig:arbiter-layer} show who writes and who reads
each record. The lock table is written and read by ACID as before, and is
now also read by both BASE paths. The claim table is written by BASE parents
and the dirty set by BASE repairs, and both are read by ACID. Each record is
therefore still written by one side only. What the arbiter adds are reads
across the two modes.

These reads are placed in the mode admission step (Step 2 in
Figure~\ref{fig:pipeline}), which is extended to also check the state of the
opposite mode. For example, when an ACID transaction goes through its mode
admission step, the arbiter checks whether any resource it needs is dirty or
claimed, by looking it up in the dirty set and in the claim table. A
transaction that fails this check is not admitted. It has already left the
pending queue, but it goes to the waiter registry or to the deferred parent
queue instead of into execution. There are two exceptions. An ACID bookkeeper
is tested in the middle of execution, when it asks for the locks it adds to its
group. A BASE repair is tested later, at rule expansion (Step 5), because that
is where it is created. The
idea is that every path checks a resource for work of the other mode before
it uses it.

The components introduced by the arbiter, both to resolve the lookup and to
handle a mode that finds a resource in use by the other mode, are the
following.

\begin{bullets}
  \item[Claim table.]\label{sec:approach-claim-table} One entry per lock
  under which an admitted BASE parent is currently writing. A parent enters
  its claims when it is admitted and removes them when it completes.

  \item[Waiter registry.] A list of observers. An ACID transaction that needs
  a dirty or claimed resource registers itself under that resource and stops.
  When the repair finishes or the claim is dropped, the registry notifies
  every transaction registered under it, and each one retries.

  \item[Deferred parent queue.] The BASE parents that met an ACID lock at
  admission. BASE transactions are not treated as observers and have a polling
  retry.

  \item[Deferred repair queue.] The BASE repairs whose target was
  ACID-locked when the rule that created them fired.
\end{bullets}

Only the claim table is a new record. The other three components, \emph{Waiter
  registry}, \emph{Deferred parent queue}, and \emph{Deferred repair queue}, hold the
transactions that found a resource in use by the other mode until that resource
is free again.

A large simplification is important to mention. The resources are split
between models, so in a real system, a lookup takes time because each model
that holds the resource has to be reached. These network calls may be slow
and can sometimes fail. The simulator sees all resources and models as one
entity, so a lookup has no latency at all and always succeeds. Modeling the
real system more closely would add a lot of overhead. The simulator,
therefore, implements the mechanism in an ideal setting, and it would be less
performant in an actual multi-model system.

\paragraph{The invariant.}\label{sec:approach-arbiter-rule} The main goal of
the hybrid implementation, and of the arbiter itself, is to enforce one
rule. A resource is never held by ACID and written by BASE at the same time.
BASE writes a resource in two ways. A BASE parent claims it, and a BASE repair
marks it dirty. This keeps the guarantees of ACID transactions intact and addresses the idea
of safe adaptation between ACID and BASE posed by RQ1. Because a resource
always has one clearly defined state, no work is lost or overwritten.
Section~\ref{sec:approach-deadlock} covers this in more detail.

\paragraph{Shared arbiter lookup position.}\label{sec:approach-enforcement}
To enforce the invariant, the pipelines of both ACID and BASE are extended
with a lookup for work of the opposite mode. An ACID root is tested at
admission, before it takes any lock. An ACID bookkeeper is tested before it
takes the locks it adds to its group. A BASE parent is tested at admission, before it
claims anything. A BASE repair is tested at rule expansion, before its
target is marked dirty.

\paragraph{ACID extended admission step.} Figure~\ref{fig:hybrid-queueing-acid}
shows how the initial ACID path was extended to look up BASE work. The diagram
is adapted from the queueing diagram of Zacouris and
Acosta~\cite{zacouris2026mxs}. This thesis extends it with the check against
the claim table and the dirty set, and with the waiter registry. An ACID transaction is tested against the claim table and the dirty
set together, and both answers have the same effect. If any resource it needs is
dirty or claimed, the transaction is paused immediately and added as a waiter to
the waiter registry. A root parked this way has not acquired any locks. It
stays in the \texttt{PENDING} state, but it is removed from the pending queue.
Figure~\ref{fig:hybrid-queueing-acid} shows that it enters the waiter registry, labeled
\texttt{DIRTY WAIT REGISTRY}, rather than the lock queue, so it holds nothing while it waits.

An ACID bookkeeper runs the same test in the middle of execution, when it asks
for the locks it adds to its group. If the test fails, the whole group is
blocked, and its members are registered as waiters. The group keeps the locks it
already holds, but it takes no new one.
Section~\ref{sec:approach-safety-liveness} explains why this still cannot lead
to a deadlock.

Two events make a resource available again. A repair that finishes clears
the dirty entry, and a BASE parent that completes drops its claims. A waiter
on a dirty resource is registered under the resource, and a waiter on a
claim under the lock id, because claims are kept per lock. All waiters
registered under the cleared key are then notified and retried. A root parked at
admission returns to the pending queue for a fresh attempt, and a bookkeeper
parked in mid-execution goes through the existing retry path.

\paragraph{BASE extended admission step.} The two BASE paths are tested
separately, because they reach a resource at different times.
Figure~\ref{fig:hybrid-queueing-base-parent} shows the parent path, and
Figure~\ref{fig:hybrid-queueing-base-bookkeeper} shows the repair path.
The parent is the foreground work and is tested at mode admission. Every resource
it needs is checked before it claims any of them. If one of them is
ACID-locked, the parent claims nothing and goes on the deferred parent
queue. Inside this queue, a BASE parent does not wait for a specific ACID
transaction. It is retried on every drain, so if the resource is still
locked, even by a lock acquired in the meantime, the parent is deferred
again rather than overrunning the lock. Once all its resources are free, the
parent returns to the pending queue and is admitted like any other. When it
completes, it drops its claims and notifies the ACID waiters registered under
them.

The repair is tested just before it would mark its target dirty. If the
target is ACID-locked, the repair is not created at all. It goes on the
deferred repair queue, the target is not marked dirty, and the transaction that
triggered it commits. Deferred does not mean waiting. The repair is retried
systematically, but there is no guarantee of when it can actually proceed.
This avoids a dependency of a bookkeeper on an ACID transaction, which could
otherwise lead to a deadlock, and it breaks no promise of eventual
consistency. When the repair is finally created, it
is created in full and processed.

This has a side effect on what is measured. The parent has already committed,
so the target is in fact out of date, but it is not in the dirty set until its
repair is created. Neither the oracle nor the reported dirty fraction counts it
during that time. The measured dirty fraction can therefore be lower than the
real inconsistency. The gap is largest in ACID mode, when many resources are
locked.

The claim table is read only by ACID. A BASE parent never checks it, and a
dirty resource does not stop it either, so BASE work never waits for other
BASE work on the same resource. This follows the idea of Salt
Isolation~\cite{xie2014salt}, where BASE transactions may see each other's
unfinished work, while ACID transactions are kept apart from it
(Section~\ref{sec:rw-static}).

Both deferred queues are polled rather than woken. Nothing signals an entry
when its lock disappears. Parents are retried once per admission step, before
anything is admitted. Repairs are retried after every batch of repairs, after
every ACID group completion, and once per simulated tick. The pass per tick
is the one that matters because a lock is also released by a group that
aborts, and an abort is not a completion. Whatever released the lock, the
entry is retried within one tick.

\paragraph{Hybrid mode limits the parent BASE
  transactions.}\label{sec:approach-base-cost} Making a BASE parent wait is
where BASE loses performance, and this cannot be avoided. BASE is meant to be
the fast mode, which processes the transaction on its own model almost
immediately and resolves the consequences in the background. In the hybrid
mode, a BASE parent can be held back at admission, so it loses part of that
speed.

A BASE parent waits only at admission, only for as long as an ACID lock is
held on one of its resources, and only while holding nothing itself. It
never blocks after it has been admitted, it never waits on another BASE
transaction, and it never waits for reconciliation. It therefore stays much
faster than an ACID transaction, but slower than in a pure BASE run.

\paragraph{Where the arbiter is deliberately
  over-cautious.}\label{sec:approach-conservatism} Two imprecisions are
built into the simulator by design.

\begin{bullets}
  \item[C1. Lock buckets hide free resources.] The two BASE checks and the
  ACID claim check read the lock of a resource and not the resource itself.
  Where a run is configured with fewer locks than resources, one lock
  covers a bucket of them, so BASE work is set aside whenever any
  resource in that bucket is locked. Transactions, therefore, wait in cases
  where they could have proceeded. At the baseline, every resource has its own
  lock (Table~\ref{tab:exp-baseline}), so C1 has no effect in the experiments
  of this thesis.

  \item[C2. Starvation of deferred work.] A deferred entry whose target
  stays locked can stay on its queue indefinitely. No entry is
  forgotten, but there is no aging rule that eventually gives a
  long-deferred entry priority over the ACID transaction keeping its
  resource busy, so under a resource that is hot for a long time,
  that work can starve. This is accepted rather than solved. Eventual
  consistency places no bound on when a repair runs.
\end{bullets}


\section{Mode oracles}\label{sec:approach-oracles}

Section~\ref{sec:approach-oracle-interface} gave a brief introduction to what an
oracle is. This section describes the two oracles that were built in this
thesis. Both use the full hybrid mechanism underneath, with the same interface,
arbiter, tagging rules, and dispatchers. They differ only in how the tag is
chosen. The \texttt{FixedShareModeOracle} is static. It is configured once at
the start of the simulation and reads no information about the system. The
\texttt{AdaptiveModeOracle} is dynamic. It reads the inconsistency level $d_k$
of the system when a transaction is admitted and uses it to choose the tag.

\paragraph{The fixed-share oracle in
  detail.}\label{sec:approach-fixed-share-oracle} The fixed-share oracle returns
ACID with a configured probability $p_{\mathrm{acid}}$ and BASE with probability
$p_{\mathrm{base}} = 1 - p_{\mathrm{acid}}$. The draw comes from a seeded
generator, so that a run can be reproduced. The tag of each transaction is
random, but the expected share of ACID transactions is fixed. Over a long run,
the measured share is close to $p_{\mathrm{acid}}$.

It was the first hybrid design, for a practical reason. The value
$p_{\mathrm{acid}}$ is set at the start of the simulation, so the oracle is easy
to configure, and it served as a proof of concept for the hybrid mode. It is
also the baseline for RQ3. It is a fixed controller that uses no feedback, and
the evaluation checks whether the adaptive oracle can perform better than it.

One design property of this oracle sets how it can be compared with the adaptive
one. What $p_{\mathrm{acid}}$ fixes is the share of \emph{transactions} tagged
to be in ACID mode. It fixes nothing about the share of \emph{time} the system
spends in ACID, because the mode of a transaction decides how long that
transaction occupies the system.

In short, this fixed-share oracle generates a controlled split of ACID and BASE
tags assigned to pending incoming transactions.

\paragraph{The adaptive oracle in detail.}\label{sec:approach-adaptive-oracle} The
adaptive oracle reads the live dirty fraction $d_k$ at the instant of the decision
and switches between two modes. It always starts in BASE mode, because throughput
should be as high as possible. As soon as the inconsistency level of the system
reaches the critical dirty threshold $c$, the oracle switches to ACID mode, and
all following transactions are tagged ACID. To get back to BASE, the
inconsistency level $d_k$ has to drop to the recovery threshold $r$.

\begin{align}
  \text{BASE} \rightarrow \text{ACID} \quad & \text{when} \quad d_k \ge c
  \label{eq:enter-acid}                                                   \\
  \text{ACID} \rightarrow \text{BASE} \quad & \text{when} \quad d_k \le r
  \label{eq:leave-acid}
\end{align}

with the interval $[r, c]$ acting as the hysteresis band
(Figure~\ref{fig:oracle-fsm}).

The oracle locks one mode for the whole system until the switch conditions are
met. Every new transaction admission is tagged with whatever that mode is at that
instant. Work that is already in flight keeps the mode it was admitted under, by
the lifetime rules of Section~\ref{sec:approach-tag}. A mode change is therefore
not an event that the running transactions experience.

The inconsistency level is the only metric the oracle uses, so every mode
transition has a single clear cause. Figure~\ref{fig:oracle-fsm} shows how the
adaptive oracle behaves when the mode switch happens and which tag a
transaction receives at each point of the run.

The two edges of the band are not symmetric. Past the critical dirty fraction, no further BASE work is
admitted, and only the BASE transactions already in flight still add dirty
resources, so the overshoot is small. The undershoot past the recovery threshold can be large. The
oracle reads the dirty fraction only when a new root transaction is tagged, and in ACID mode, this happens rarely.
Reconciliation keeps clearing the dirty set between two readings, so the reading
that triggers the switch is often well below the recovery threshold.
Section~\ref{sec:recovery-mechanism} gives more details.

\paragraph{The critical dirty and recovery
  thresholds.}\label{sec:approach-parameters-oracle} The oracle has two
parameters. The critical dirty threshold, also called the inconsistency level
threshold, is the fraction of resources that may be dirty before the oracle stops
issuing BASE tags. It states in the configuration how much inconsistency the
system is willing to accept.

The recovery threshold is the fraction the system must reconcile back down
to before BASE resumes. The reconcilers work in both modes. What changes in
ACID mode is that new transactions no longer add dirty resources, so the
reconcilers can catch up. Both thresholds are fractions of the resources,
and the recovery threshold $r$ is configured directly
rather than derived from the critical dirty threshold $c$, subject to $0 \le r \le c$.

The two extremes of that range are worth naming, because they are policies and
not just values. At $r = c$, the band has zero width, and the only anti-flap
mechanism in the design is gone. The
simulator accepts this configuration, but it is not a recommended setting, and no
experiment in this thesis uses it. At $r = 0$, the rule says reconcile everything
before resuming BASE, which differs from a small $r$, because an ACID visit then
ends only when the dirty set is empty, so its length is set by the reconciler
pool alone.

\paragraph{The oracle reads the inconsistency level at
  admission.}\label{sec:approach-sampling}\label{sec:approach-samplers} The oracle
reads the dirty fraction inside the call that assigns a mode. That is once per
untagged root transaction, at its first admission attempt. Nothing else triggers
a reading. The simulation tick does not force one, and no reading is taken while
the system is progressing but admits nothing.

This ties the rate at which the oracle reads the dirty fraction to the rate at
which new root transactions arrive. Under \texttt{EQUILIBRIUM}, the transaction
population is held constant, so arrivals follow completions, and the reading
rate of the oracle is about the throughput. When the adaptive oracle is in ACID
mode, the throughput drops strongly, and so does the reading rate.
Section~\ref{sec:effective-recovery} measures the consequences.

The reported measurements of the dirty fraction are not taken this way. The
reading of the oracle is part of the system under study. The reported
measurements come from a separate reader that runs once at the end of each
simulated tick, regardless of mode or load. The percentiles of the dirty
fraction in Chapter~\ref{chapter:experiments}, such as $p_{95}$, are taken over
these per-tick readings. Only the levels at a mode switch are readings of the
oracle.

Reading $d_k$ only at admission is still enough, because a reading matters only
when a transaction has to be tagged. A reading once per tick would record the
switch to BASE closer to $r$, so the measured undershoot would be smaller. It
would not change the behavior of the system, because it would not let any BASE
transaction start earlier. Under \texttt{EQUILIBRIUM}, a new root transaction is
created only when an in-flight one finishes. In ACID mode, these transactions are
long, and they hold the admission capacity while reconciliation clears the dirty
set in the background. The first BASE transaction is therefore admitted at the
same moment with either kind of reading.

\paragraph{Collision probability of ACID
  transactions and dirty resources.}\label{sec:approach-blocking-cost} The
arbiter makes an ACID transaction wait on every dirty resource it needs. Under
the adaptive oracle, the dirty fraction stays close to the critical dirty
threshold, so its size is roughly known. This allows us to model a useful
quantity, the probability that one ACID transaction has to wait on a dirty
resource. The cost comes from the arbiter and not from the choice of the tag,
so it applies to the fixed-share oracle as well.

One parameter has to be explained before the derivation. The baseline value
$L = 50$ (\texttt{maxTransactionResources}) is the maximum number of resources
one transaction can touch. The simulator draws the resource count $\ell$ of each
transaction uniformly from $1$ to $L$. The derivation assumes that these
resources are independent of each other and that each of them is dirty with
probability $d$.

In this setup, a single resource is clean with probability $1-d$. A transaction
with $\ell$ resources is clean only if every one of them is clean, so the
probabilities multiply.

\begin{equation}
  P_{\text{clean}}(d) \;=\; \underbrace{(1-d)\cdot(1-d)\cdots(1-d)}_{\ell \text{ resources}}
  \;=\; (1-d)^{\ell}
  \label{eq:clean-probability}
\end{equation}

Blocking is the complementary event, in which at least one of the $\ell$
resources is dirty.

\begin{equation}
  P_{\text{block}}(d) \;=\; 1 - P_{\text{clean}}(d) \;=\; 1-(1-d)^{\ell}
  \label{eq:blocking-probability}
\end{equation}

Figure~\ref{fig:blocking-probability} plots this probability against the dirty
fraction $d$ from $0$ to $0.12$ for two cases. The first is the worst case
$\ell = L = 50$. The second is the average over all transaction sizes $\ell$
from $1$ to $50$. The figure shows that blocking is not a rare event, but the
normal case for an ACID transaction admitted while the dirty set is large. The
dirty fraction is not always as high as $c = 0.10$. But even at the baseline
recovery threshold $r = 0.05$, an average ACID transaction is blocked by a
dirty resource with a probability of 65\%. In addition,
Equation~\ref{eq:blocking-probability} ignores the resources claimed by BASE
parent transactions, which makes the probability even higher.

This paragraph shows the additional cost that the arbiter introduces in a
hybrid run, whichever oracle issues the tags. ACID transactions now have to wait not only on the
locks of other ACID transactions, but also on the resources claimed by BASE
parents and on the dirty resources left by BASE bookkeeper transactions.
Unfortunately, this is unavoidable because otherwise the isolation promise of
ACID would be broken.

\paragraph{A weighted average of the dirty fraction as a considered
  design.}\label{sec:approach-nofilter} One design decision taken along the way
was to smooth the inconsistency level before the oracle looks at it. The
thresholds were not compared against the inconsistency level $d_k$ directly, but against an
exponentially weighted moving average (EWMA) $\bar{d}_k$ of it. At every reading,
the average was updated with the smoothing factor $\alpha$.

\begin{equation}
  \bar{d}_k \;=\; \alpha \, d_k + (1 - \alpha) \, \bar{d}_{k-1},
  \qquad 0 \le \alpha \le 1, \qquad \bar{d}_0 = d_0
  \label{eq:ewma}
\end{equation}

At $\alpha = 1$, the average is equal to the live value $d_k$, so there is no
smoothing. The baseline smoothing factor was $\alpha = 0.2$. This means that a
new reading $d_k$ contributed only 20\% to the average.

A filtered signal was expected to reduce noise and to avoid rapid mode switches.
That decision was reversed, and the adaptive oracle now reads the live dirty
fraction $d_k$ at the moment of admission. The smoothing was removed for three
reasons.

\begin{bullets}
  \item[The dirty fraction is an exact value.] The dirty fraction is an exact number
  maintained by the simulator, and it has no measurement noise. The filter,
  therefore, had nothing to remove. It only delayed real changes of $d_k$.
  In addition, the anti-flap work was already done by the hysteresis band
  (Section~\ref{sec:prelim-hysteresis}).

  \item[The switch at the critical dirty threshold was unaffected.] In earlier runs with the filter,
  which are not reported in this thesis, the measured $p_{95}$ of the dirty
  fraction stayed within about one percentage point of the critical dirty threshold at every setting of
  the smoothing factor. The BASE $\to$ ACID switch, therefore, behaved the same
  way with and without the filter.

  \item[It increased the undershoot of the recovery threshold.] The smoothing added
  a second lag to the ACID $\to$ BASE switch, on top of the gap between two
  readings described above. As a result, the
  system became much cleaner than configured before BASE resumed, and the
  recovery threshold had little effect.
\end{bullets}

\paragraph{The hybrid mode is designed to work with any
  oracle.}\label{sec:approach-other-oracles} The two oracles of this section are
only two possible policies. The hybrid mode itself does not depend on how a tag
is issued. The dispatchers, the arbiter, and the tagging rules work with any
component that implements the \texttt{ModeOracle} interface. A new policy,
therefore, only needs one new class, which is connected through the hybrid
runtime assembler.

For example, other policies could focus on the throughput or on the length of
the pending queue, or they could use a learned policy like the one used by
Hybrid Transactional Replication~\cite{kobus2018htr}. Every such oracle
also keeps the safety properties of Section~\ref{sec:approach-deadlock}, because
they come from the arbiter and not from the choice of the tag.

\section{Safety of the hybrid mode}\label{sec:approach-deadlock}

RQ1 asks how a system can add a hybrid mode that adapts between ACID and
BASE \emph{safely}.

\paragraph{What safe means in this
  work.}\label{sec:approach-safety-what}

\begin{bullets}
  \item[S1. Transactions never corrupt each other's work.] A resource is never
  under an ACID lock and written by BASE at the same time, neither claimed by
  a BASE parent nor marked dirty by a BASE repair. This is the
  invariant of Section~\ref{sec:approach-arbiter-rule}. It is the property that
  keeps the ACID promise. Otherwise, the results of one transaction could
  overwrite the work of another and corrupt the state of the system.

  \item[S2. No work is dismissed or forgotten.] Every transaction that is made
  to wait is looked at again, and keeps being retried for as long as it
  waits. Nothing that is
  parked or deferred is forgotten or silently dropped.

  \item[S3. Every run is free of deadlock.] The simulator never reaches a state
  in which work is waiting, but none of it can proceed.
\end{bullets}

Two things are not part of this definition on purpose. Safety here says nothing
about how long a wait lasts. It also says nothing about fairness, so one piece
of work can be delayed much longer than another. S2 promises only that the work
is still there and is still retried, not that it runs soon.

\paragraph{S1 holds because of the shared arbiter
  design.}\label{sec:approach-safety-defined} In a pure run, each mechanism reads
only its own records, and that is enough, because the records of the other mode
are always empty. In a hybrid run, the records of both modes are in use at once,
so each side has to consider the work of the other. The arbiter of
Section~\ref{sec:approach-arbiter-lookup} places a check on every path that
uses a resource. There are four such paths. These are the ACID root at
admission, the ACID bookkeeper when it adds locks, the BASE parent at admission,
and the BASE repair at rule expansion (Section~\ref{sec:approach-enforcement}).
Every transaction, therefore, verifies whether the resources it needs are
available. If one of them is not, the transaction waits until it is able to
proceed.

\paragraph{S2 holds because every waiting entry is looked at
  again.}\label{sec:approach-safety-progress} The two waiting structures avoid
dismissing outstanding work in two different ways.

The ACID transactions registered as waiters are all woken as soon as the
resource they wait on is available again. This works the same way for dirty and
for claimed resources. The waiters are notified as soon as
the event happens.

The deferred queues, on the other hand, are polled because the event that
matters to them is not visible in the same way. Nothing tells a deferred entry
that a lock is gone. Each deferred entry is therefore retried at fixed points of
the simulation, which are described in Section~\ref{sec:approach-enforcement}.
Nothing guarantees when a BASE transaction will be able to proceed, but every
entry is retried at least once per simulation tick. As mentioned in the previous
sections, polling fits BASE, since, by design, this mode aims only at eventual
consistency.


The hybrid mode, therefore, either keeps a waiting transaction in a monitored
structure, where it is notified on a specific event, or polls it systematically.
No transaction is dropped or deleted while it waits.


\paragraph{S3 holds because no new wait cycles are
  introduced.}\label{sec:approach-safety-liveness} A deadlock is a cycle of
transactions in which each one holds something that the next one waits for.
Figure~\ref{fig:deadlock-freedom} shows the three ways one transaction can end
up waiting for another in a hybrid run, and only the first of them has a cycle.
That first one comes from the base simulator, which already breaks it by
aborting one group.

The two waiting mechanisms added by this thesis cannot close a cycle. A deferred
BASE entry holds nothing, so no transaction can wait on it. An ACID waiter is
different. A root parked at admission holds nothing either, but a bookkeeper
parked in mid-execution keeps the locks of its group. That wait still cannot be
part of a cycle, because what it waits on never waits itself. A dirty resource
is cleared by a repair that has already been created and needs no lock. A claim
is dropped by a BASE parent that has already been admitted and never blocks
again. Neither of them can wait on the parked group, so the wait always ends.

  \caption{The three kinds of waiting in a hybrid run.}

    \item[2] ACID waits on BASE work that never waits back.

As Figure~\ref{fig:deadlock-freedom} shows, the arbiter adds waiting but no new
cycle. Two further points follow from that. First, the arbiter can add aborts.
A group whose bookkeeper is parked in the waiter registry is blocked and keeps
its locks. Under the first abort rule of
Section~\ref{sec:approach-group-locking}, another ACID transaction that asks for
one of those locks is aborted instead of being queued. Second, the rest of the cost of
waiting shows up as time.

\paragraph{The known imprecisions do not break safety.} The two imprecisions of
Section~\ref{sec:approach-conservatism} do not weaken the three properties,
because both of them err in the same direction. Under C1, coarse lock
granularity makes the BASE checks look at a whole bucket of resources instead of
one. Work can then be deferred that did not have to be, which costs time but
never breaks S1. Under C2, a deferred entry whose resource stays locked for a
long time can be significantly delayed. That is a case of starvation rather
than deadlock, so S2 and S3 still hold.

\paragraph{The properties hold by
  construction.}\label{sec:approach-safety-limits} The three properties are
established by design and not by measurement. S1 holds because the four
checks sit on the four paths that use a resource, and there is no fifth path. S2
and S3 hold because of the shape of the waiting that those checks produce. No
experiment in this thesis was designed to test these properties directly.
